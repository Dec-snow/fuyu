## 一、整体分层

```text
┌─────────────────────────────────────────────────────────────┐
│  WebView2（React + TypeScript）                              │
│  ┌───────────┐  ┌──────────────┐  ┌───────────────────────┐ │
│  │ 组件/渲染  │←→│ Zustand store │←→│ services/api.ts       │ │
│  └───────────┘  └──────────────┘  │ services/events.ts    │ │
│         ↑                          └───────────┬───────────┘ │
└─────────┼──────────────────────────────────────┼─────────────┘
          │                Tauri IPC              │
          │   invoke(command)  ⇄  emit("chat-event")
┌─────────┴──────────────────────────────────────┴─────────────┐
│  Rust（src-tauri）                                            │
│                                                               │
│  commands/          命令边界：参数校验、错误结构化             │
│      ↓                                                        │
│  api/openai.rs      「语义层」：内部模型 ⇄ OpenAI JSON        │
│  api/sse.rs         「字节层」：网络分片 ⇄ 完整 SSE 事件       │
│      ↓                                                        │
│  storage/           SQLite（历史）+ providers.json（配置）     │
│                     + keyring（API Key）                       │
│  state.rs           共享 HTTP 客户端 + 取消令牌表             │
│  window/            托盘 / 全局热键 / 悬浮窗生命周期           │
└───────────────────────────────────────────────────────────────┘
```

三条硬边界：

1. **前端拿不到 API Key**。Key 只在 Rust 侧读取并拼进 `Authorization` 头，
   前端能问到的只有 `hasKey: bool`。
2. **前端不认识任何厂商 JSON**。厂商差异全部在 `api/openai.rs` 里被归一化成
   `ChatEvent`；换厂商不用改前端一行。
3. **前端不直接操作窗口**。`show/hide/setSize` 都走自己的命令，权限面收敛到
   `core:default`，位置记忆、动画兜底、模式持久化都留在 Rust 侧。

## 二、一次流式对话的完整生命周期

```text
[前端] 用户按 Enter
   │
   ├─ 1. 生成 requestId（前端生成，不是后端）
   ├─ 2. save_user_message 落库            ← 先落库，网络失败也不丢用户输入
   ├─ 3. 计算 history 快照（含刚落的 user 消息，不含助手占位）
   ├─ 4. 插入一条空气泡（streaming: true）
   │
   ├─ 5. invoke chat_send({ providerId, modelKey, requestId, ... })
   │        │
   │        ├─ Rust: 校验 → 查配置 → 从凭据管理器取 Key → 拼 URL
   │        ├─ Rust: register_cancellation(requestId) → CancellationToken
   │        ├─ Rust: async_runtime::spawn(run_stream)
   │        └─ Rust: 立刻返回 requestId
   │
   │   ┌──── run_stream（后台任务）────────────────────────────┐
   │   │ emit Start                                            │
   │   │ send_with_retry()  ← 只在拿到 2xx 之前重试             │
   │   │ loop {                                                │
   │   │   select! { token.cancelled() | stream.next() }        │
   │   │   SseParser::push(bytes)   → Vec<String>（完整事件）   │
   │   │   parse_stream_chunk(ev)   → ChunkParts               │
   │   │   合批 → emit Delta / ReasoningDelta                   │
   │   │   finish_reason 到了 → 再宽限 1500ms 等 usage          │
   │   │ }                                                     │
   │   │ parser.finish()  ← 冲刷未闭合事件（否则丢最后一句）     │
   │   │ emit Usage                                            │
   │   │ 落库助手消息 + 首次自动命名 + 顶 updated_at            │
   │   │ emit Finish                                           │
   │   └───────────────────────────────────────────────────────┘
   │
   └─ 6. 事件经 chat-event 通道到达 events.ts
          → seq 去重 → 分发到 chat store → 更新对应气泡
```

### 为什么 `requestId` 必须由前端生成

`chat_send` 返回之前，Rust 就已经开始 emit 事件了。如果 ID 由后端随机生成，
前端可能在 `await invoke(...)` 返回之前就收到第一个 `delta`，此时路由表里还没
有这条映射 —— 事件被丢弃，用户看到的是一段没有开头的回答。

前端先生成 ID 再传进去，这个竞态就从根上消失了。这是一个**协议设计**问题，
不是加锁能解决的。

## 三、SSE 解析：为什么拆成两层

参考项目最值得抄的一处设计。`api/sse.rs` 只懂字节协议，连 `[DONE]` 都不认识；
`api/openai.rs::parse_stream_chunk` 只懂 OpenAI 语义，完全不碰换行和字节。

好处：

- 两层都能做**纯函数单测**，不需要网络（本项目 30 个测试里 30 个都不联网）；
- 换厂商只改语义层；换传输（WebSocket）只改字节层；
- 各自的失败模式互不污染。

### 三个必须记住的细节

**1. 按裸字节 `0x0A` 切行是 UTF-8 安全的。**

UTF-8 的续字节范围是 `0x80..=0xBF`，永远不等于 `\n`，所以行边界不可能落在
多字节字符中间，被切断的半截字符自然留在 `buf` 里等下一个分片。

**但前提是只对完整行做 `from_utf8_lossy`。** 先对整个 `buf` 解码再切行，半截
中文字符会被替换成 `�` —— 这就是 LLM 客户端中文乱码的头号成因。

本项目的 `utf8_split_mid_character_is_safe` 和
`every_multibyte_char_split_at_every_offset` 两个测试守着这条：后者把一个含
`你好世界🌍` 的 payload 在**每一个字节位置**切开，断言拼起来和一次喂进去完全一致。

**2. `data:` 后面只去掉一个空格。**

规范是 `data:` 后跟一个可选空格，用 `trim_start()` 会把模型输出里有意义的
缩进（代码块首行）也吃掉。

**3. `finish_reason` 到了不能立刻结束流。**

OpenAI 在带 `finish_reason` 的**下一片**才发 usage，而大量中转根本不发。
本项目的做法：

```rust
// 终止条件
if finished && usage.is_some() { break; }

// 已结束时只再宽限一小段时间等 usage
let next = if finished {
    tokio::select! {
        _ = token.cancelled() => None,
        item = timeout(USAGE_GRACE_MS, stream.next()) => item.unwrap_or(None),
    }
} else {
    tokio::select! {
        _ = token.cancelled() => None,
        item = stream.next() => item,
    }
};
```

配套两个必须做的怪癖修复：

- `"finish_reason": ""` 必须当作**未结束** —— 有的服务端每一帧都带这个空串，
  当成结束的话用户只能看到一个字的回答（`empty_finish_reason_means_not_finished` 测试）；
- 请求体要带 `stream_options.include_usage`，否则很多中转永远不给 token 用量。

## 四、重试的边界：只在流开始之前

```rust
match request.send().await {
    Ok(resp) if resp.status().is_success() => return Ok(resp),  // ← 重试到此为止
    ...
}
```

一旦已经返回 2xx，后面无论流怎么断都**不重试**。原因是：已经有 delta 推给前端了，
重试会把同一段回答再拼一遍，用户看到「你好你好」。

所以：

| 阶段 | 失败表现 | 策略 |
|---|---|---|
| 建连 / DNS | 连接错误 | 重试，最多 3 次，指数退避 + 抖动 |
| HTTP 4xx/5xx | `429` / `5xx` | 重试（`Retry-After` 优先，封顶 10s） |
| HTTP 401/403/404/400 | 鉴权、端点、参数错 | 不重试，直接报错 |
| 流中途断 | `stream.next()` 返回 `Err` | **不重试**，报「流式连接中断」 |

另外：`Retry-After` 必须在**消费 body 之前**读 —— body 一读完，响应头就跟着没了。

还有一处刻意的取舍：`reqwest::Client` **不设全局 `timeout`**，只设
`connect_timeout(10s)`。SSE 回答可能跑几分钟，总超时会在回答说到一半时把它掐死。
运行期的终止靠 `CancellationToken` 主动取消。

## 五、取消：令牌表 + `select!`

```rust
// state.rs
pub cancellations: Arc<Mutex<HashMap<String, CancellationToken>>>,
```

`chat_send` 注册令牌 → 把 `token.clone()` move 进后台任务 → `chat_cancel` 只是
`token.cancel()` → 流循环里的 `select!` 立刻走取消分支。

要点：

- 后台任务**无论怎么结束**都要从表里摘掉自己的令牌，否则这张表会一直涨；
- 取消时已经收到的半截回答**照常落库** —— 用户看到过它，历史里就该留着；
- `State<'_, T>` 是一个借用，不能跨 `.await` 持有、也不能 move 进 `spawn`。
  真正带进任务的是 `Arc` 的克隆（`cancellations.clone()`、`db.clone()`、
  `state.client()`）。

## 六、数据存储：三个地方，各管一摊

| 存储 | 放什么 | 为什么 |
|---|---|---|
| SQLite | 会话、消息、token 用量 | 需要查询、事务、全文检索 |
| `providers.json` | 服务商、模型列表、界面偏好 | 人可读、可手改、可备份；**不含密钥** |
| Windows 凭据管理器 | API Key | 系统级加密，不落普通文件 |

### 迁移：`user_version` 驱动 + 幂等加列
```rust
let current: i64 = conn.query_row("PRAGMA user_version", [], |r| r.get(0))?;
if current > target { return Err(...); }   // 旧程序打开新库 → 拒绝，别写坏数据
for (index, step) in MIGRATIONS.iter().enumerate() {
    let version = index as i64 + 1;
    if version <= current { continue; }
    let tx = conn.unchecked_transaction()?;
    match step { /* Sql | AddColumn */ }
    tx.pragma_update(None, "user_version", version)?;
    tx.commit()?;                          // 每步一个事务，失败即回滚
}
```

参考项目用「匹配 `duplicate column name` 这句英文错误串」来判断列是否已存在 ——
脆弱（SQLite 换版本或换语言就失效）。本项目改成先查 `PRAGMA table_info`：

```rust
enum Step {
    Sql(&'static str),
    AddColumn { table: &'static str, column: &'static str, decl: &'static str },
}
```

`migrations_reach_the_target_version` 测试会连开两次数据库，确认第二次不报错。

### FTS5 trigram：中文检索不引任何依赖

```sql
CREATE VIRTUAL TABLE messages_fts USING fts5(
    content, content='messages', content_rowid='rowid', tokenize='trigram'
);
```

- `content='messages'` 是**外部内容表**：FTS 表本身不存正文，只存索引，正文
  永远以 `messages` 为准，不会有两份数据不同步；
- 代价是删除 / 更新必须显式走 `'delete'` 指令 —— 靠 3 个触发器同步；
- **trigram 分词器**把文本按三字符滑窗建索引，对中文天然是子串匹配，
  不需要任何分词库、更不需要向量模型。

两个必须处理的边界：

1. trigram 至少要 3 个字符才有索引可用 → 短词回退 `LIKE`；
2. 用户输入里的 `"` 会让 `MATCH` 语法报错 → 包成短语并转义：
   `format!("\"{}\"", q.replace('"', "\"\""))`。

`deleting_a_conversation_clears_its_search_index` 测试守着「级联删除后
FTS 索引也必须同步清掉」—— 这是外部内容表最容易出的静默 bug：不报错，
但搜索结果里会出现已经删掉的会话。

### 参考项目没做、本项目补上的两点

| 项 | 参考项目 | 本项目 |
|---|---|---|
| `journal_mode` | 未设（默认 delete） | `WAL` |
| `busy_timeout` | 未设 | `5000ms` |

单连接 + 单实例下不设也能跑，但只要将来加一个后台连接（比如用量统计线程）
就会立刻撞 `SQLITE_BUSY`。属于「现在不做，将来一定会痛」的项。

## 七、窗口生命周期：三个容易翻车的地方

### 1. 「按了快捷键窗口一闪而过」

程序化 `show()` 之后，系统会立刻送来一次 `blur`。如果失焦隐藏逻辑不加闸门，
窗口会在同一帧被自己关掉。

解决：Rust 侧 `show_and_focus` 里 emit `window-shown`，前端收到后
`guardBlur(700ms)`；`App.tsx` 的 blur 处理里先检查时间戳。

### 2. 「渲染进程卡住 → 得到一个关不掉的窗口」

退场动画由前端播，播完调 `finish_hide`。但如果渲染进程卡死或崩了，这个回调
永远不来，窗口就留在屏幕上了，用户只能去任务管理器杀进程。

解决：Rust 侧挂一个 320ms 的兜底线程：

```rust
HIDE_PENDING.store(true, Ordering::SeqCst);
std::thread::spawn(move || {
    std::thread::sleep(Duration::from_millis(HIDE_GRACE_MS));
    if !HIDE_PENDING.swap(false, Ordering::SeqCst) { return; }  // 前端已回报
    handle.run_on_main_thread(move || { win.hide(); });
});
```

### 3. 「唤出动效飞回了窗口移动前的位置」

`set_position()` 是**异步**的，紧接着 `outer_position()` 读到的还是旧值。
参考项目的注释里明确记了这个坑。

解决：目标位置是**算**出来的，不是读回来的 —— `resolve_position()` 返回一个
`PhysicalPosition`，先算完再 `set_position`。

### 另外两处细节

- 窗口动画全部由前端 `transform` / `opacity` 驱动，后端不参与逐帧移动。
  每一帧调 `set_position` 会走系统窗口管理器，抖动且昂贵。
- 去掉窗口阴影（`set_shadow(false)`）后 Windows 11 会连带丢掉圆角，
  需要显式 `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE, DWMWCP_ROUND)`
  要回来 —— 否则入场动效会先暴露窗口真实尺寸，看起来像闪了一下。

## 八、错误处理：结构化而不是字符串

参考项目命令统一返回 `Result<T, String>`，前端只能把整句话显示出来。
本项目定义：

```rust
pub struct AppError {
    pub code: String,       // unauthorized / rate_limited / network / ...
    pub message: String,    // 给用户看的中文
    pub retryable: bool,    // 前端据此决定要不要给「重试」按钮
}

impl serde::Serialize for AppError { /* → {code, message, retryable} */ }
```

于是前端可以按 `code` 分支（401 → 跳设置页、429 → 显示重试），而不是去匹配
文案。Rust 侧的 `From<rusqlite::Error> / From<reqwest::Error> / From<io::Error>`
让命令里可以直接用 `?`。

**安全纪律**：任何 `Authorization` 头、API Key、请求体都不得出现在 `message`
里，也不得写日志。

## 九、前端：为什么是 4 个 store，而不是 7 个

参考项目 7 个 store（chat / providers / settings / window / assistants /
imagegen / history）。本项目 MVP 只保留：

| store | 职责 | 对应参考项目 |
|---|---|---|
| `config` | `providers.json` 的全部内容 + 主题应用 | settings |
| `providers` | 服务商 / 模型 / Key 状态 | providers |
| `chat` | 会话列表 + 当前消息 + 流式路由表 | chat + history |
| `ui` | 展开状态、设置面板、动画阶段、blur 闸门 | window |

拆分的依据是**状态的生命周期**，不是页面。同一个 store 里的状态一起加载、
一起失效；跨 store 的交互走 `useX.getState()`（zustand 的 store 外读取），
不需要额外的胶水层。

### 唯一的 Tauri 事件监听器

`services/events.ts` 里只 `listen` 一次，然后同步分发给订阅者。若每个组件各自
`listen`，增量事件高频到达时会有 N 个 IPC 监听器。去重与终态清理的算法本身在
`lib/event-gate.ts`（一个不依赖 Tauri 的纯类，可以直接单测）。

### 在飞的消息不属于 `messages`

`lib/chat-state.ts` 把「当前会话已落库的消息」和「正在生成的那条」分开：

```ts
messages: UiMessage[]                      // 当前会话，已落库
live: Record<conversationId, UiMessage>    // 在飞，按它所属的会话索引
routes: Record<requestId, { messageId, conversationId }>
```

界面上显示的是两者拼接（`visibleMessages`）。这么分的原因见下一节第 4 点。

### 窗口先渲染、数据就绪、最后 show

`tauri.conf.json` 里窗口是 `visible: false` 启动的。`main.tsx` 的顺序是：

```text
接事件桥 → 拉配置 → 拉服务商 → 拉会话 → setWindowMode → showWindow → 播入场动画
```

这样用户永远不会看到一闪而过的白屏。代价是启动多花几十毫秒 —— 值得。

## 十、第二轮：功能测试驱动的重构

第一版能跑通之后做了一轮系统性功能测试（Rust 端对本地假 SSE 服务端跑真 HTTP，
前端补 vitest）。结果里大部分不是「代码写错了」，而是**没有被任何测试覆盖的分支**。
这一节记录改了什么、以及原来的写法为什么不对。

### 1. 流式循环没法测 → 拆出 `api/stream_client.rs`

原来的 `run_stream` 直接持有 `AppHandle` 和 `Database` —— 这两样在测试里几乎
无法构造（一个要真的 Tauri 应用，一个要临时库），而真正想验证的其实是
「网络字节 → 事件」这一段。

拆成两层之后：

| 模块 | 职责 | 测试方式 |
|---|---|---|
| `api/stream_client.rs` | 重试策略、SSE 消费、`finish_reason` 宽限期、取消 | 起本地假服务端，跑真实 HTTP |
| `commands/chat.rs` | 校验、装配、落库、广播 | 只剩纯函数单测 |

`send_with_retry` / `consume_stream` 只依赖 `reqwest::Response` 和
`CancellationToken`，于是测试里可以 `TcpListener::bind("127.0.0.1:0")` 起一个
假服务端，用 chunked 编码一段一段把数据喂出来。

**顺带发现了这个拆分最大的收益** —— 一个只有写测试才会暴露的真 bug：
原来是 `ParsedChunk::Done => break 'outer`，会跳过紧随其后的 `flush_pending`。
后果是**当 `delta` 和 `[DONE]` 落在同一个 TCP 分片里时，正文会进数据库，
但从来没有推给前端**：用户看到一条空消息，重新打开会话才发现里面有内容。

现在有 `content_and_done_in_the_same_chunk_is_not_lost` 守着它。

### 2. Tauri 的 `async` 命令必须返回 `Result`

把 DB / 凭据相关的命令改成 `async` 时踩到的：Tauri 用「返回类型是不是 `Result`」
来区分成功与错误两条 IPC 通道，所以 `async fn foo() -> T` 直接编译不过，
必须写成 `-> AppResult<T>`。

为什么要改成 `async`：**Tauri 里没有 `async` 的命令跑在主线程上**。这些命令要读
系统凭据管理器（一次 OS 调用，可能十几毫秒）和做带 `fsync` 的配置落盘，压在
主线程上就是直接卡住界面渲染。改 `async` 之后它们被丢到 tokio 运行时执行。

### 3. 「发多少历史」需要一条明线：`agent/context.rs`

原来只校验「条数 ≤ 200、单条 ≤ 20 万字」—— 理论上一次请求能塞进四千万字。
聊久了必然撞上模型的上下文窗口，然后收到一个含糊的 400。

现在 `agent/context.rs` 做三件事：

- `estimate_tokens`：CJK 按 1 token/字、其他按 1 token/4 字符粗估。
  刻意**高估** —— 高估只是多丢一点历史，低估会直接 400；
- `fit_context`：从**最旧**的开始丢，但最后一条永远保留、最近两条一定保留、
  裁剪后不能让上下文以 `assistant` 开头（部分服务端会 400）；
- 把丢了多少条通过 `ChatEvent::ContextTrimmed` **告诉前端**。

最后这点不是锦上添花：静默截断会让用户以为模型「忘了」前面说过的话，
比直接报错更难排查。

> 参考项目在这里有个真实缺陷：它的 `fit_context` 执行**之后**才把知识库、技能、
> 搜索结果拼进系统提示词，于是那几块完全不受 32k 预算约束。本项目的顺序是
> 「所有注入 → 统一裁剪」，没有重犯。

### 4. 前端：在飞的消息不能放在 `messages` 里

原来流式回答的气泡直接 push 进 `messages`。一旦用户切到别的会话，
`selectConversation` 会整个替换 `messages`，于是：

- 那条正在生成的回答消失了；
- 后续 `delta` 找不到归属，被静默丢弃；
- 切回去也看不到它（要等生成结束、重新从数据库读）。

改成把在飞消息单独放 `live: Record<conversationId, UiMessage>`，`messages` 只表示
「当前会话已落库的内容」。除了修掉上面三条，还有个额外收益：
**流式期间 `messages` 的数组引用完全不变**，配合 `React.memo`，每个 delta 只重渲染
那一条气泡，而不是整个历史。一次长回答可能有上千个 delta，这个差别很直观。

### 5. 「重新生成」会把用户那句话存两遍

`regenerate` 原来复用了 `send(text)` 的路径，而 `send` 会调 `save_user_message`。
于是每点一次「重新生成」，同一个问题就在数据库里多一份。

修法是让两者共用一条 `submit({ newUserText, history })` 路径：`newUserText` 传了才
落库，重新生成时不传。顺带把旧回答从库里删掉 —— 否则反复重新生成会堆出一串
没人会看的回答，下次打开会话全显示出来。

### 6. 逐字符落盘

设置面板里 `temperature` 是滑块、系统提示词是文本框，两者原来都是
`onChange → patch`。而 `patch` 走的是 `update_settings` —— 每次一次
「临时文件 + fsync + rename」的原子写。

结果：拖一次滑块几十次 fsync，敲一篇 500 字的提示词 500 次 fsync。

改成「拖动 / 打字只改本地草稿，停手 300~500ms 或失焦才提交」。

### 7. 其余几处

| 症状 | 根因 | 修法 |
|---|---|---|
| 搜 `a\` 返回错误结果 | `LIKE` 转义漏了转义反斜杠**本身**，`\%` 被解释成「字面百分号」 | 先转义 `\` 再转义 `%` `_`，并把顺序写进注释 + 单测 |
| 会话时间偶尔没更新 | 插消息和顶 `updated_at` 是两条独立语句，中间失败就留下不一致 | 合成一个事务 `append_assistant_turn` |
| 空字符串渲染出一个空段落 | `"".split("\n")` 得到 `[""]`，被当成一个文本块 | 丢弃纯空白的文本块 |
| 新增配置字段有让老配置整个读不出来的风险 | 依赖容器级 `#[serde(default)]`，一旦被谁删掉就会静默丢配置 | 加测试钉死「老文件必须能读、缺的字段回落默认值」 |

## 十二、第三轮：P0/P1 能力补全

第二轮把「主链路」做扎实了，但它只覆盖了一个**顺利**的问答：答完、存下、显示。
第三轮补的是那些「不顺利」和「不够用」的部分 —— 失败、长会话、改问题、
让模型动手、把外部的字和网页拿进来。

这一章按实现的顺序讲，每节都是同一个结构：**要解决什么 → 怎么做 → 为什么这么选 → 代价**。

### 1. P0-1 失败的消息也要落库

**问题**：原来只有成功（且有正文）的回答才写库。于是一次失败之后：

1. 前端把那条在飞气泡清掉（`settleConversation` 里丢掉 `live[convId]`）；
2. 数据库里没有记录；
3. 下一次打开这个会话，那条失败的对话**凭空消失**了 —— 用户既看不到
   「为什么没答出来」，也没有可以点的「重试」。

**做法**：给消息加两个字段。

```rust
pub enum MessageStatus { Ok, Cancelled, Error }
pub struct StoredMessage {
    // ...
    pub status: MessageStatus,
    pub error: Option<AppError>,   // 序列化进 error_json 列
}
```

- 迁移 **v7** 加 `status TEXT NOT NULL DEFAULT 'ok'`，**v8** 加 `error_json TEXT`；
- `append_assistant_turn` 多收两个参数，把 `AppError` 序列化成 JSON 存进 `error_json`；
- 落库条件从「有正文」改成「有正文 **或** 状态是 Error」——
  一次失败即使一个字都没生成，也必须留下痕迹；
- 前端 `toUiMessages` 把 `status` 翻译成 `cancelled: boolean` 与 `error: AppError | null`，
  气泡据此渲染「已停止生成」或错误条 + 重试按钮。

**为什么存整个 `AppError` 而不只存一句话**：`code` 决定前端怎么分类展示，
`retryable` 决定要不要给重试按钮。只存 message 字符串，这些判断就全丢了。
所以 `AppError` 从「只实现 `Serialize`」改成了 `#[derive(Serialize, Deserialize)]`。

**代价**：`error_json` 里可能有服务端返回的原文（含请求细节）。它只落在本机
SQLite 里，和会话正文同样对待。

**重试怎么做**：`retry(messageId)` 找到这条消息**之前**的历史，删掉它和它之后
的所有消息，再以那段历史重新提问。删掉旧回答是刻意的 —— 保留的话，
用户会看到同一个问题下面挂着两个互相矛盾的答案。

### 2. P0-2 虚拟列表：几百条消息只渲染视口内的

**问题**：`messages.map(...)` 在长会话下会一次挂载几百个 DOM 子树。
每个气泡里还有 Markdown 解析结果，滚动直接卡住。

**做法**：`react-virtuoso`。

```tsx
<Virtuoso
  data={messages}
  computeItemKey={(_, m) => m.id}
  followOutput={(isAtBottom) => (isAtBottom ? "smooth" : false)}
  increaseViewportBy={{ top: 600, bottom: 600 }}
/>
```

三个细节值得记住：

- **`computeItemKey` 必须给**。默认按下标做 key，而虚拟列表会换掉窗口内的
  数据，下标 key 会让 React 复用错组件，表现为「滚动时内容串行」；
- **`followOutput` 收一个函数**，参数是「当前是否在底部」。返回 `false` 表示
  「别跟」—— 这样用户往上翻历史时，不会被正在生成的文字拽回底部。
  固定返回 `"smooth"` 是这类组件最常见的体验事故；
- **`increaseViewportBy`** 上下各多渲染 600px，减少快速滚动时的白屏。

**为什么 `React.memo` 在虚拟列表下依然有用**：虚拟化只解决「同时挂载多少个
气泡」，不解决「一秒钟重渲染多少次」。流式期间每收到一个 delta 都会 `set()`
一次，视口内的已落库气泡引用没变，`memo` 能拦住它们 —— 每个 delta 只重绘
正在长的那一条。

**代价**：包体从 191 KB 涨到 255 KB（`react-virtuoso` 约 60 KB）。
它是这一轮唯一新增的运行时依赖。

**另一个坑**：切会话时要滚到底部。直接 `scrollToIndex({index:"LAST"})` 会落空，
因为新消息还没渲染、Virtuoso 还没测量出目标项。放进 `setTimeout(..., 0)` 里，
等这一帧渲染完再滚。

### 3. P0-3 编辑重发：中间那条改了就重跑

**问题**：用户发现自己第三条问错了，想改。原来只能删掉整个会话重来。

**做法**：双击用户气泡进入编辑态 → `editAndResend(messageId, newContent)`：

1. `update_message` 改库；
2. 把这条**之后**的所有消息全部删掉（数据库 + 界面）；
3. 历史 = 这条之前的部分 + 编辑后的内容；
4. 走 `submit({ history })` 重发。

**为什么必须删掉后面的消息**：它们是基于旧问题生成的。留着就是一条
**幽灵分支** —— 模型看到的历史里，那个问题已经不是它回答的那个问题了。

**界面细节**：编辑态是气泡的**局部** `useState`，不进 store。理由：同时只会有
一个气泡在编辑，把它提升到全局状态只会让 store 多一个「哪个 id 在编辑」的
字段，以及随之而来的清理逻辑。

**一个容易漏的点**：只能编辑**已落库**的用户消息。还没落库的乐观气泡
（`local_` 前缀的 id）在数据库里没有对应行，改它会静默失败。

### 4. P1-1 Agent 工具系统

这是这一轮最大的一块。目标：让模型能真的动手 —— 读时间、算数、碰剪贴板、上网。

#### 4.1 没有 `Tool` trait

参考项目用 `trait Tool { fn name(&self); async fn run(&self, args); }` +
`Vec<Box<dyn Tool>>`。本项目**故意不这么做**：

```rust
pub struct ToolDefinition {        // 纯数据
    pub name: &'static str,
    pub description: &'static str,
    pub parameters: Value,         // JSON Schema
    pub sensitive: bool,           // 执行前要不要审批
    pub exfiltrates: bool,         // 会不会把数据发出去
}

pub async fn execute(name: &str, args: &Value, ctx: &ToolContext) -> ToolResult {
    match name {
        "calculator" => calculator(args),
        "read_clipboard_text" => read_clipboard_text(),
        "fetch_webpage" => super::web::run_fetch_webpage(args).await,
        // ...
    }
}
```

理由：trait 的价值是**多态替换** —— 在不改调用方的前提下换一个实现。
但工具列表在编译期就固定了，替换的收益是零，代价却是
`Box<dyn Tool>` + `async trait` + 生命周期标注 + 无法直接单测。

**加一个工具 = 数组里加一项 + `match` 加一个分支**，两处都在同一个文件，改起来一眼可见。

#### 4.2 策略字段绝不下发给模型

```rust
ToolDefinition { name, description, parameters, sensitive, exfiltrates }
                       ↓ 只导出这三个
{ "type": "function", "function": { "name", "description", "parameters" } }
```

`sensitive` / `exfiltrates` 是**本地策略**，模型拿到了只会尝试绕过
（提示词注入的第一课就是「告诉模型这个工具不需要审批」）。有一个单测专门把
导出结果序列化成字符串，断言里面**不出现**这两个词。

#### 4.3 agent 循环

`run_stream` 从「发一次、收完、结束」变成了一个最多 5 轮的循环：

```text
循环（最多 MAX_AGENT_STEPS = 5 次）：
  1. 组请求体（带 tools）→ 发送 → 消费流
  2. outcome.tool_calls 为空？→ 这就是最终回答，跳出
  3. 把 assistant 的 tool_calls 追加进消息历史
  4. 逐个执行工具（敏感的先审批），把结果作为 role="tool" 消息追加
  5. 回到 1
```

配套改动：

- `StreamOutcome` 多一个 `tool_calls: Vec<ToolCall>`；
- 工具调用是**分片到达**的（`delta.tool_calls[].function.arguments` 是字符串增量），
  所以 `consume_stream` 里用一个 `BTreeMap<usize, (id, name, args_buf)>` 按
  `index` 累积，流结束时才组装成完整调用；
- `ChatMessage` 加 `tool_calls` / `tool_call_id` / `name` 三个可选字段，
  `messages_to_openai` 据此产出规范形态（assistant 消息 `content: null` + `tool_calls`，
  tool 消息带 `tool_call_id`）；
- **即使工具执行失败，也必须回灌一条 `tool` 消息** —— 少一条，下一轮请求会
  因为「有 tool_calls 却没有对应 tool 结果」被服务端直接 400。

#### 4.4 三级授权

```rust
pub enum ApprovalScope { Once, Session, Always }
```

| 档位 | 存哪 | 何时失效 |
|---|---|---|
| 允许一次 | 不存 | 立刻 |
| 本次会话允许 | `AppState.session_tool_approvals`（内存 `HashSet<(session_id, tool_name)>`） | 应用退出，或换一个 `approval_session_id` |
| 永久允许 | `providers.json` 的 `always_allowed_tools` | 用户手动清掉 |

「本次会话」的键里带 `approval_session_id`（前端传会话 id），所以**换会话就换
scope** —— 即使应用没重启，新会话也不会沿用旧会话的授权。

实现上，走审批的工具会：

1. 建一个 `oneshot::channel`，把发送端存进 `AppState.tool_approvals`（键 `request_id:call_id`）；
2. 发 `ToolPending` 事件给前端，卡片上显示参数（联网工具就是完整 URL）；
3. `tokio::select!` 同时等「用户裁决」「取消」「60 秒超时」；
4. `chat_approve_tool` 命令按 `request_id:call_id` 取出发送端并 `send(verdict)`。

**数据流防泄漏**是叠在上面的一层：`ToolResult.touched_local_data` 一旦置位
（读了剪贴板），本轮上下文**再发给模型服务商之前**会触发一次不可记住的确认
（`can_remember: false`）。它防的是这个链路：

```text
读剪贴板（用户批准）→ 上下文里有本地数据 → 下一次请求把它发给模型服务商
```

**外发型工具（`fetch_webpage`）不给「永久允许」**：`can_remember = !exfiltrates`。
它的 URL 由模型生成，被注入的模型可以把对话内容塞进查询串。
每次都要用户看着 URL 点头，这是唯一可靠的防线。

#### 4.5 计算器为什么不 `eval`

模型给的是**不可信输入**。任何能执行代码、调用函数的求值器都是注入面。
所以手写了一个只认「数字 + 四则运算 + 括号 + 一元正负号」的递归下降解析器，
其他字符一律报「无法识别的字符」。有单测专门喂 `__import__('os')`、`1; rm -rf /`。

### 5. P1-2 划词助手 `Alt+Q`

**问题**：Windows 没有「读取当前选区」的公开 API。

**做法**：业界通行办法（uTools、Snipaste 都这么做）——
**记住剪贴板 → 模拟 Ctrl+C → 轮询 → 还原剪贴板**。

三个必须处理的细节：

1. **等修饰键松开再发 Ctrl+C**。热键触发时 `Alt` 还物理按着，注入的 Ctrl+C 会变成
   `Alt+Ctrl+C`，没有程序会把它当复制。用 `GetAsyncKeyState` 轮询 Alt/Shift/Win，
   松开了才继续（Ctrl 不等 —— 复制本来就需要它）；
2. **窗口必须在复制之后才显示**。模拟按键只会到达「当前拥有选区的那个窗口」，
   如果先把助手窗口显示并聚焦，按键就打进我们自己的输入框了，取词永远失败。
   所以顺序是：阻塞抓取 → `run_on_main_thread` 里 `show_and_focus` → 再发事件；
3. **内容没变 = 复制没发生**。如果轮询到的新内容和按热键前一模一样，说明没选中
   任何东西（或目标窗口被 UAC 挡住），继续等也是白等。这条判断抽成了纯函数
   `is_fresh_copy(previous, current)`，五个单测覆盖空串 / 纯空白 / 内容相同等情况。

**已知限制**：模拟按键无法到达管理员权限（UAC 提升）的窗口 —— Windows 会挡住从
普通完整性进程发往更高完整性进程的 `SendInput`。这时明确报错，而不是静默失败。

**`Alt+Q` 很抢手**（输入法、截图工具都爱占），所以设置里可以改。改键用的是和唤醒键
同一套「**先注册再落盘**」逻辑：注册失败则配置不变，不会进入「配置里写着一个
抢不到的键」的死状态。

### 6. P1-3 滚动摘要

**问题**：上下文超预算时 `fit_context` 从最旧开始丢 —— 丢了就是真丢了，
用户会发现模型把前面说过的彻底忘了。

**做法**：把要丢的那段交给模型自己压成摘要，留在提示词里。

```text
会话变长 → plan_summary 决定折叠区间 → 调一次非流式补全生成摘要
        → 存进 conversations.summary + summary_message_count
        → 下一轮只把「摘要 + 该条之后的原文」发给模型
```

**两个容易做错的地方**：

1. **折叠边界必须落在一条 `user` 消息上**。把「提问」折进摘要、却把它的「回答」
   留在原文里，剩下的上下文就以 `assistant` 开头 —— 不少服务端会直接 400。
   `plan_summary` 会从 `total - SUMMARY_KEEP_RECENT` 往后找到第一条 `user`；
2. **摘要自己也吃预算**。它是一条真实的 `system` 消息，所以要先从总预算里
   扣掉它的估算 token，再让原文去抢剩下的额度。另外 `MAX_SUMMARY_CHARS` 封顶 2000 字，
   不让摘要无限膨胀。

**增量合并**：`previous_summary` 非空时，提示词是「把新增对话合并进已有摘要」，
而不是从头重写。否则每次摘要都要重读全部历史，成本和延迟随会话长度线性增长。

**`dropped` 与 `summarized` 是两个字段**：前者是**真丢了**，后者是**改用摘要替代**。
混在一起会让前端提示变成「已省略 50 条」，而实际上一条都没丢 —— 这是会误导用户的。

**摘要失败不打扰用户**：它只是优化，挂了不该让一次已经成功的问答看起来像出了问题。
所以 `maybe_summarize` 只 `eprintln`，不发 Error 事件，而且放在终态事件**之后**，
不拖慢「回答结束」的那一刻。

**迁移 v9 / v10** 加 `conversations.summary` 与 `summary_message_count`。
注意 `set_conversation_summary` **不动 `updated_at`** —— 摘要是后台压缩产生的，
不该让一个旧会话因此跳到会话列表最前面。

### 7. P1-4 安全抓取：六道闸门

`fetch_webpage` 的参数是**模型给的**。被提示词注入的模型会用它去请求
`http://169.254.169.254/`（云元数据，能换到临时凭据）、`http://127.0.0.1:11434/`
（本机服务）、`http://10.0.0.5/admin`（内网后台）。所以每次请求都要过白名单：

| 闸门 | 防的是什么 |
|---|---|
| 1. 只允许 `http` / `https`，URL 不得内嵌用户名密码 | `file:` 读本机文件、`data:`、解析器混淆 |
| 2. **DNS 解析出的每一个 IP** 都必须是公网 | 一个域名同时有公网和内网记录 |
| 3. 把主机名**钉死**在已校验的那个 IP 上 | DNS rebinding：校验时返回公网、连接时返回内网 |
| 4. **重定向自己跟**，每一跳重走 1–3 | 公网 URL 302 到内网 |
| 5. 响应体**流式限长**（512 KB） | 坏站点把内存吃光 |
| 6. 单跳超时 15 秒、最多 5 跳 | 挂住不返回 |

IP 黑名单覆盖回环 / 私有网段 / 链路本地（`169.254/16`，云元数据就在这）/
运营商级 NAT（`100.64/10`）/ 组播 / 保留段，以及**能封装内网 IPv4 的 IPv6 形式**
（IPv4-mapped、6to4、Teredo）—— 最后这几类是常见绕过点。

#### 写这段代码时被测试抓出来的一个真漏洞

第一版用 `url.host_str()` 拿主机名再 `parse::<IpAddr>()`。测试喂进
`http://[::1]:8080/` 时**没有报错** —— 因为 `host_str()` 对 IPv6 字面量返回的是
**带方括号**的 `"[::1]"`，`parse::<IpAddr>()` 失败，于是代码认为「这不是 IP，
是个域名」，接着去查域名黑名单，自然也不匹配，最后放行了。

修法是改用类型化的 `url::Host` 枚举（`Ipv4` / `Ipv6` / `Domain`），
IPv6 分支直接拿到 `Ipv6Addr` 去判断。测试里也补上了 `[::ffff:127.0.0.1]`
这种 IPv4-mapped 的方括号写法。

这件事值得单独记一笔：**SSRF 这类防护不能靠「我以为的字符串形态」**，
必须用解析器给出的类型。测试不是走过场 —— 它真的抓到了一个能让内网暴露的 bug。

#### HTML 转文本：故意不引依赖

`scraper` / `html2text` 都能做得更精确，但这里的目标只是「让模型读得懂正文」。
手写一个约 80 行的转换器：删掉 `script` / `style` / `head` 整段与注释，
块级标签换成换行，剥掉其余标签，解码常见实体（含 `&#123;` 与 `&#x1F600;`），
最后收敛空白。少一个解析库就少一片攻击面。

#### 联网搜索：配了才出现

搜索走 SearXNG 的 `format=json` 接口。没有配置端点时，
`to_openai_tools(web_search_enabled = false)` **不下发**这个工具 ——
模型看不到就不会去调一个没配置的服务，也就不会白烧一轮 token。

搜索端点复用同一套 `safe_get`，但 `allow_private_ips = true`：
自建 SearXNG 常常就在局域网里（`http://192.168.1.10:8888`），
而且这个地址是**用户在设置里填的**，不是模型给的 —— 威胁模型不同。
（同样的道理，本项目的聊天服务商预设本来就允许 `http://localhost:11434/v1`。）

### 8. P1-5 图片输入：多模态的代价在「怎么传」上

**问题**：让用户粘贴 / 拖一张图进来，连同问题一起发给视觉模型。

OpenAI 兼容接口的形态是这个样子 —— `content` 从字符串变成**数组**：

```json
{"role": "user", "content": [
  {"type": "text", "text": "这是什么？"},
  {"type": "image_url", "image_url": {"url": "data:image/png;base64,..."}}
]}
```

#### 8.1 一个必须想清楚的设计问题：图片怎么传到后端

最直觉的做法是「前端把图片 data URL 塞进 `content` 一起发给 `chat_send`」。
但本项目的请求模型是**每次都把整个会话历史发过来**（§四），于是：

> 一个 10 轮、每轮 2 张图的会话，每问一次就要在 IPC 上搬
> 10 × 2 × 2 MB ≈ **40 MB** 的 base64。

这个量级明显不可接受。所以改成：

```text
前端                                    后端
─────────────────────────────────────────────────────────
粘贴图片 → data URL（只为本地预览）
点发送 → save_user_message(content, images)  ← 图片只传这一次
                  ↓ 落库 messages.images_json
        chat_send(history: [{id, role, content}])
                  ↓
        按 id 批量取图（一条 IN (...) 查询）→ 塞进 content 数组
```

两个好处：

- **IPC 负载与图片数量无关**，历史里永远只有文字；
- 图片在库里是**单一来源**，多轮对话里模型每轮都能看到那张图，
  不需要前端反复回传。

配套的两个细节：

1. `attach_images` 在 **`fit_context` 裁剪之后**才跑 —— 被裁掉的消息不必去查图，
   少一次无用的查询；
2. `submit` 里要把历史中「还没落库的那条用户消息」补上 `id`。
   不补的话，**刚发出去的这张图这一轮模型反而看不到**（因为查不到 id）。
   这是个非常容易漏的点，而且症状是「第一次发图没反应，第二次追问才有效」。

#### 8.2 图片存哪：为什么选 SQLite 而不是文件

| 方案 | 好处 | 代价 |
|---|---|---|
| 存文件 + 库里存路径 | 库文件小 | 删会话时要手动删文件，还要处理「写了一半」的孤儿文件；需要引用计数 |
| **存库（data URL）** | 删会话即删图，完全交给外键级联；事务一致 | 库文件变大 |

MVP 阶段选了后者：**正确性优先于体积**，而且省掉了一整类「孤儿文件」的 bug。
上限由 `save_user_message` 把关：**一条消息最多 4 张，单张 data URL ≤ 3 MB**
（≈ 2.2 MB 二进制）。

#### 8.3 安全：data URL 必须是白名单

图片最后要进 WebView 的 `<img src>` 渲染，所以这里有个**真实的 XSS 面**：

- `data:text/html;base64,...` 里的脚本**会执行**；
- `data:image/svg+xml,...` 里可以塞 `<script>` 或 `onload=`。

因此 `is_supported_image_data_url` 用的是**白名单**（png / jpeg / webp / gif），
而不是「排除几个危险类型」的黑名单 —— 后者永远会漏。

校验发生在**两个**地方，因为有两个入口：

1. `save_user_message`（正常路径，落库前）；
2. `validate_request`（防前端绕过第一个入口直接塞图片）。

#### 8.4 前端：`FileReader` 而不是 Tauri 的文件 API

粘贴 / 拖拽进来的 `File` 用 `FileReader.readAsDataURL` 读成 data URL。
这样 WebView 里直接 `<img src>` 就能预览，也不需要额外开启
`fs` 插件权限（多一个插件就多一片攻击面）。

粘贴事件里有个细节：

```ts
// 只有真的带图时才 preventDefault，否则会破坏正常的文字粘贴。
if (files.some((f) => f.type.startsWith("image/"))) {
  event.preventDefault();
  void addFiles(files);
}
```

#### 8.5 迁就现实的一处

`ChatMessage.content` 保持 `String`，**没有**改成
`Text | Vec<ContentPart>` 的枚举。多模态只在 `messages_to_openai`
这一个地方展开成数组形态。

理由：`content` 被 `estimate_tokens`、`fit_context`、`summary`、
落库、搜索等一大片代码当作字符串用。改成一个枚举，就要在这些地方全部加
`.text()` 适配 —— 而收益只是「类型上更精确」。把复杂度**收在一处**
（适配器）比散到十处更好维护。有一个单测专门钉住：
**无图消息必须保持字符串形态**，免得将来顺手全改成数组、把兼容性搞坏。

### 9. 顺带修掉的两处

**配置损坏不再静默丢数据**。原来 `providers.json` 解析失败就回落默认值，
而用户下一次改设置会把默认值写回去 —— 里面的服务商配置就永久没了。
现在先把损坏文件改名留档（`providers.json.corrupt-<时间戳>.json`）再回落，
并且解析前剥掉 UTF-8 BOM（记事本保存 UTF-8 会带 BOM，`serde_json` 不接受）。

**非流式请求只有一处实现**。滚动摘要需要一次「要完整结果、不要逐字上屏」的调用，
而「测试连接」早就手写过一遍同样的 post + 超时 + 状态码 + 取正文。
于是抽出 `api/complete.rs::complete_once`，两边共用 ——
少一份重复就少一处会忘记同步修的 bug。

| 取舍 | 现状 | 什么时候需要改 |
|---|---|---|
| 工具沙箱 | 只有 SSRF 白名单 + 审批，没有进程级隔离 | 要执行真正危险的本地操作（删文件、跑命令）时，需要独立进程 + 权限降级 |

## 十三、第四轮：专项审计与修复

前几轮都是「照着参考项目补功能」，功能齐了之后就进入了一个更麻烦的阶段：
**没人能一眼看出哪里是坏的**。这一轮换了做法 —— 开四路审计，各自只盯一小块、
必须给出「怎么触发」的场景，然后逐条复现、修掉、补测试。

四个方向：后端聊天链路、前端状态机、UI/交互、存储与网络。
结论先放前面：**4 个方向一共 47 条有效缺陷**（含 1 条 Critical、5 条 High），
另有 5 条「看起来像 bug 但实际正确」的项被逐条排除。

### 1. 最重要的一条：摘要会把用户的提问吃掉

这是这一轮唯一的 Critical，也是最值得写下来的一条 —— 它把一个**位置参数**
用在了两套不同的坐标系上。

切上下文时原本这样做：

```rust
// agent/context.rs（修复前）
let covered = covered.min(messages.len());
let tail = &messages[covered..];   // 丢掉前 covered 条
```

`covered` 来自数据库的 `conversations.summary_message_count`，意思是
「摘要把前面多少条压缩过了」。问题在于：

- 它是**数据库行数**；
- 而要切的是**前端发来的那个数组**，两者并不等长：
  - 前端会过滤掉「正文为空且没有图片」的消息（历史里的失败轮就是这种）；
  - 用户「编辑重发」会把某条之后的**一堆消息删掉**，行数立刻变少，
    而 `summary_message_count` 还停在旧值上，没有任何东西会去改它。

于是 `messages[covered..]` 会错位。最坏的情况：删到 `covered >= messages.len()`，
`tail` 变成空数组 —— 发给模型的请求里**只有一条摘要，没有用户刚问的那句话**。
模型对着摘要编一个回答，而且这个错误会一直重复（计数永远修不回来）。

**修法：不用位置，用身份。** 迁移 v12 给 `conversations` 加一列
`summary_covered_message_id`，记下摘要覆盖到的**最后一条消息 id**：

```rust
// 找得到边界，才敢切；找不到就整段放弃摘要。
let Some(index) = covered_message_id
    .and_then(|id| messages.iter().position(|m| m.id.as_deref() == Some(id)))
else {
    return fit_context(messages, system_prompt, budget_tokens);
};
let tail = &messages[index + 1..];
if tail.is_empty() {
    return fit_context(messages, system_prompt, budget_tokens);
}
```

定位失败（那条被删了 / 被前端过滤了）就**整段放弃摘要**：宁可多发一段历史、
甚至因此触发常规裁剪，也绝不能丢用户的提问。`summary_message_count` 保留下来
只用于界面显示「较早的 N 条已压缩」。

配套还做了两件事：

- `maybe_summarize` 选边界时，从区间末尾往前找第一条**有正文或有图片**的消息 ——
  拿一条空消息当边界，下一轮必然定位失败，摘要就白做了；
- `update_message_content` / `delete_message` 在同一个事务里**作废该会话的摘要**
  （摘要描述的是旧正文，改完就用它等于在骗模型）。

### 2. 第二重要：配置会被静默覆盖掉

`providers.json` 在文档里是「人可读、可手改、可备份」的。原来的读取逻辑是：

```rust
match std::fs::read_to_string(&path) {
    Ok(text) => { /* 解析；失败则留档 + 写默认值 */ }
    Err(_)   => { /* 当成首次启动，直接写一份预设 */ }
}
```

`Err(_)` 把**所有** IO 错误都当成了「文件不存在」。可是文件存在但内容不是合法
UTF-8 时（记事本存成 ANSI / UTF-16LE、PowerShell 5.1 的 `>` 默认就是 UTF-16），
`read_to_string` 报的是 `InvalidData` 而**不是** `NotFound` —— 于是用户手改过的
配置连同 9 个服务商一起被预设覆盖，既没有留档，也没有任何提示。

修成两件事：

1. 只有 `ErrorKind::NotFound` 才走「首次启动」分支；其它 IO 错误一律走留档路径；
2. `quarantine()` 改成返回 `Option<PathBuf>`。改名失败时（Windows 上文件被占用、
   没有 `FILE_SHARE_DELETE` 时 `rename` 会失败）**什么都不写**，只把默认值放在内存里 ——
   因为 `File::create` 照样能把那个文件清空，而日志里还会写着「已留档到 <原路径>」，
   等于一边毁数据一边撒谎。

顺带修掉 `ConfigStore::update` 的一个隐患：闭包自己返回 `Err` 时原来不回滚内存，
于是「界面显示已生效、重启又变回去」，而且下一次任何成功的写入会把这个
**被拒绝的值**悄悄落盘。

### 3. HTML 转文本：两个把正文吃光的写法

`strip_element` 用 `<head` 做前缀匹配去删 `<head>…</head>`。可是：

- `<header>` 也以 `<head` 开头（现代网页几乎页页都有），而 `</header>` 同样匹配
  `</head` —— 夹在中间的正文整段被删；
- HTML5 **允许省略** `</head>`，原来的 `None => cursor = len` 会把后面整个 body 丢掉，
  模型只拿到「来源：URL」，然后对着空白编答案。

修法是「校验标签边界」+「找不到闭合标签时按标签语义区别对待」：
`script` / `style` 的内容本身就是要丢的东西，没闭合就整段丢弃；
`head` 这类没闭合只跳过开标签，正文照常输出。

同一次还发现 `decode_entities` 的数字实体循环是 O(n²)：`find("&#")` 每次都从头扫、
`replace_range` 每次都挪尾部。512 KB 上限内能塞十万个实体，实测能让一个 tokio
工作线程空转好几秒 —— 而这段文本是**别人控制的网页**。改成一次前向扫描后是 O(n)。

### 4. 前端：一整套「只写不读」的状态

这一轮前端最刺眼的发现是：`useChat.error`、`useConfig.error`、`useProviders.error`、
`useUi.notices` 这四路状态**一直在被写入，却从来没有任何组件读过**。
后果是相当多的失败完全静默：

> 刚装好、还没配模型 → 打一句话按回车 → 输入框清空了，没有气泡、没有转圈、
> 也没有任何文字。看起来就是「这软件坏了」。

修法是加一个提示条组件，并把「哪几路来源 → 显示成什么」抽成纯函数
（`lib/toasts.ts`），这样能直接断言「每一路都有对应的提示项」——
不必为了测它去搭一个 DOM 环境。

同类的还有几个**竞态**，都靠把状态机抽出来直接驱动来验证：

| 缺陷 | 触发场景 | 修法 |
|---|---|---|
| 结算会误删新一轮 | 回答刚结束就立刻发下一条 | `settleConversation` 带上「结算的是哪一条」，期间有新请求就整体不动 |
| 并发闸门不原子 | 编辑长会话时连按两次回车 | `streamingId` 要等几次 IPC 才设上，改成一个**同步**落下的 `submitting` |
| 切会话不清空消息 | 点开会话 B 后立刻发送 | 拿到的历史是 A 的，请求却发往 B —— 会话间数据串台 |
| 重试先删后发 | 切到没配 Key 的模型上点「重新生成」 | 旧回答被删掉、新请求必然失败，用户两头落空 |
| 编辑时丢了图片 | 编辑一条带图的消息再重发 | 历史里那条消息传了 `id: null`，后端按 id 取图就取不到 |
| Esc 冲突 | 悬浮窗里编辑消息按 Esc | 「取消编辑」和「关掉窗口」撞在同一个键上 |

### 5. 后端：几个「安静地做错事」的地方

- **工具结果不设上限**：`fetch_webpage` 能返回 512 KB，原样回灌历史会让
  **下一轮**请求远超上下文预算（十万 token 量级），服务端直接 400 ——
  而工具其实已经执行过了。现在单个工具结果截到 8000 字符并明确标注「已截断」，
  让模型知道该怎么继续。
- **摘要请求不设上限**：贴过超长文档的会话，第一次折叠就会构造出一个
  必然超限的请求 —— 它**永远**失败，而每一轮成功的问答之后都会原样重试一次，
  白烧一次 API 调用，覆盖进度还永不前进。现在会把折叠区间收缩到预算内
  （边界仍落在 `user` 消息上），一次折不完就分多次，进度单调前进。
- **5 轮工具用满后静默收场**：最后几轮的工具有结果、模型却没机会作答，
  原来直接当作正常完成 —— 前端收到 `Finish`，气泡在结算时消失，
  用户既没看到回答也没有可重试的锚点。现在明确报错。
- **审批的「永久允许」只在后端判**：外发型工具不允许永久放行，
  前端把按钮置灰了，但那条命令本身可以被直接调用。降级逻辑放进
  `effective_scope(requested, can_remember)`，顺带变成可单测的纯函数。
- **取消不打断工具执行**：联网工具最长能跑十几秒，原来点了「停止」要干等，
  而且像「写剪贴板」这种**有副作用**的工具在取消后照样生效。现在用
  `tokio::select!` 把工具执行也纳入取消。
- **`complete_once` 的超时只包了 `send()`**：一个只回响应头、然后挂着不吐 body
  的服务端（企业代理、坏掉的中转）会让「测试连接」永远转下去。超时改为覆盖
  整次交互。

### 7. 顺带确认「不是 bug」的几条

审细一点容易把正确的东西也报成缺陷，这里记下几条**核对后确认正确**的，避免以后
有人照着「修」：

- **SSRF 的 IP 判断是完整的**。`url` 2.5 实现了 WHATWG 的 IPv4 解析，
  所以 `2130706433`、`0x7f.1`、`0177.0.0.1`、`127.1`、`127.0.0.1.` 全都会以
  `Host::Ipv4` 的形式送进来，不会绕过黑名单；`localhost.`（带点）虽然不在域名
  黑名单里，但会被下一层「解析出来的地址逐个检查」拦住。
  唯一真正的缺口是只处理了 IPv4-mapped 而漏了 IPv4-compatible（`::a.b.c.d`），
  这一轮补上了（实测当前 Windows 栈根本连不通，属于纵深防御）。
- **SSE 解析没有多字节切片问题**：按原始 `0x0A` 切分，只对完整行做
  `from_utf8_lossy`，且 `line[0]` / `line.last()` 都有长度判断。
- **FTS5 的查询串转义是对的**，`"""`、`a"b`、`***`、`x AND y` 之类都不会报错。
- **列下标与 mapper 完全对齐**，迁移新增的列都追加在 SELECT 列表末尾，
  没有历史列错位。
- **前端没有 XSS 面**：没有任何 `dangerouslySetInnerHTML`，模型输出走 React 元素；
  本地虽然能把 SVG 读成 data URL，但 `<img>` 里的 SVG 不执行脚本，
  而且后端在落库前就拒了非位图格式。

### 8. 补齐：后端有能力、前端没入口

审计的另一半产出是「**已实现但够不着**」的功能。这类缺陷不会报错，只会让用户
以为「这软件做不到这件事」。这一轮补齐了四处，它们有个共同点：
**命令和 store 方法都写好了，就是没有组件调用**。

| 能力 | 之前的状态 | 现在 |
|---|---|---|
| 自定义服务商 | `upsert_provider` 支持「带新 id 进来就是新建」，但界面上只能改预设的 Base URL —— 想接自建 / 中转网关完全没办法 | 「模型」页签底部多了一个添加表单（名称 + Base URL + 可选模型名） |
| 删除服务商 | `delete_provider` 和 `useProviders.remove` 都在，**零调用点**；预设不允许删（后端会拒） | 自定义服务商卡片出现「删除」按钮，连带清理凭据管理器里的 Key |
| 撤销「永久允许」 | 审批卡上给出的永久授权会写进 `providers.json`，但没有任何界面能查看或撤销 —— 只能手工编辑配置文件 | 「通用」页签列出已授权的工具（可点胶囊逐项撤销、也可一键全撤） |
| 系统代理 | `use_system_proxy` 存进了配置、`apply_proxy` 也接受它，但 `build_http_client` **从来没读过** —— 勾不勾都一样 | 真正生效：显式 `proxy_url` 优先，否则按开关决定是否 `no_proxy()` |
| 会话列表 | 固定拉 200 条且没有分页，第 201 个会话永远够不着 | 「加载更多」每次 +200，到后端硬上限 1000 时如实提示「更早的请用搜索」 |

两点值得展开：

**为什么「存了却没人读」比「没实现」更糟。** 前者会让用户以为功能存在、
反复尝试；而且它会污染配置文件，让后来读代码的人以为这个字段有意义。
所以处理方式只有两种：让它生效，或者把它删掉 —— 这一轮选了前者。
另外 `no_proxy()` 的默认值特意设成 `true`（跟随系统/环境变量），
因为默认 `false` 会让「什么都没配」的用户在无感知的情况下**失去**环境变量代理，
那不是我们该替用户做的决定。

**新增的撤销入口反过来要求后端收紧。** `always_allowed_tools` 现在可以由前端
整表覆写，所以后端必须校验：只接受**已知工具名**（`sanitize_always_allowed`）。
不校验的话，一份被篡改的配置就能预先「永久允许」一个以后版本才会出现的工具 ——
而这条白名单是敏感工具唯一的守门人。顺带做了去重和排序：
界面顺序稳定，配置文件也不会因为顺序抖动被反复改写。

### 9. 补齐时又挖出来的一个真 bug：代理到不了联网工具

给「系统代理」接线的时候顺手查了一下，发现了一个更实的问题：
**用户配的代理对联网工具完全无效。**

原因是联网工具刻意不共用共享的 `reqwest::Client` —— 它要逐跳把主机名钉死
在已校验的 IP 上（`ClientBuilder::resolve` 只能在构造时设置），所以每一跳
都自己新建客户端。结果就是：**聊天走代理、抓网页和搜索直连**。

在必须走代理的网络里，这等于「模型能用、工具全废」，而且失败信息是
「请求失败」，完全指不到代理这个原因。修法是把代理显式传进 `ToolContext`，
再一路带到 `safe_get` 的每跳客户端。

顺带发现同一段代码还有一个连带的脆弱点：`safe_get` **无条件**在本地解析
目标主机名（为了逐个校验 IP 是不是公网）。而企业网络里很常见的形态是
「本机 DNS 不出网、只留一个 HTTP 代理」—— 那种环境下本地解析必然失败，
于是即便代理配好了，工具还是全军覆没。

现在的策略是分情况：

- 解析成功 → 仍然逐个校验是否公网，并钉死 IP（防 rebinding），**保持原样**；
- 解析失败且配了代理 → 交给代理去解析（连接本来就是代理发起的），不钉 IP；
- 解析失败且没有代理 → 照旧报错。

安全上的取舍写在这里：配了代理之后，「目标最终连到哪里」由代理决定，
我们拿不到证据 —— 这是把信任边界交给了用户自己配置的代理。但字面内网 IP、
内网域名、以及**能解析出来**的内网地址仍然一律拒绝，所以防护没有整体退化。

两条测试把它钉住：

- `the_configured_proxy_is_actually_used_by_the_web_tools` —— 起一个假代理，
  用一个**解析不出来**的域名去抓，断言代理收到的请求行是绝对形式
  （`GET http://…`），这是「真的经过代理」的直接证据；
- `without_a_proxy_an_unresolvable_host_still_fails` —— 反向确认，
  不加代理时解析失败就该失败，没有被上面那条宽松分支放过。

这一条很值得记下来：**「参数加了」和「参数被用了」是两件事**。
接线类的 bug 不会报错，只会让用户觉得「这功能时灵时不灵」。

## 十四、第五轮：真机实测（拿假服务端戳真界面）

前面四轮都是「读代码 + 单测 + 静态检查」。这一轮换了打法：**把应用当成黑盒，
用脚本真去点它**。结论很直接 —— **实测抓到了一个四轮审计都没看出来的 bug**，
而且是「功能宣称做了、实际没生效」的那一类。

### 1. 怎么做的：假服务端 + 外部驱动

| 部件 | 作用 |
|---|---|
| 假 OpenAI 服务端（本地 HTTP） | 实现 `/v1/models` 与 `/v1/chat/completions`（含 SSE）。**每个请求都记一行日志**；用关键词控制行为（普通回答 / 慢速分片 / 发 `tool_calls` / 非流式假摘要） |
| 外部窗口驱动 | 用 `SendInput` 级别的 API 点击、打字、按键；用 `IsWindowVisible` / `WindowFromPoint` 反查状态 |
| 旁证 | 直接读 `floatai.db`（落库结果）和 `providers.json`（设置是否真的写盘） |

这样做的价值在于**三个证据链互相独立**：界面上的变化、服务端收到的请求、
数据库里的行。单测只能看其中一个。

### 2. 教训：驱动脚本必须先证明「窗口真的在最上层」

这一轮有一半的调试时间浪费在**脚本自己在骗自己**：应用窗口被别的窗口盖住了，
点击和打字全部送进了别人的窗口 —— 界面上毫无变化，而脚本却以为自己正在测应用。
更麻烦的是「看起来有窗口」也可能骗人：`.app` 初始 `opacity: 0`，所以
**窗口对象存在、`IsWindowVisible` 为真、但整页全透明**也是可能的。

所以驱动脚本现在有两条硬性前置检查：

1. `WindowFromPoint(窗口中心)` 得到的那个顶层窗口，必须属于应用的进程 ——
   不满足就直接报错退出，绝不继续打字；
2. 需要判断「界面有没有反应」时，用**改动像素数**而不是肉眼：截图 → 操作 → 再截图 → 求差。

这两条一加上，后面每一次操作才真的可信。

### 3. 抓到的真 bug：点「停止」之后，那半截回答没落库

现象：发一条会慢慢吐字的提问，点「停止」→ 界面上半截回答在，
但 `messages` 表里**只有 `user` 那一行**，`assistant` 一行都没有。
切走再切回来（或重开应用）那半截回答就消失了 —— 而且因为没落库，
连「重试」的锚点都没有。README 里写的「停止生成：已生成内容照常落库」
**实际是失效的**。

根因就一行顺序：

```rust
let outcome = consume_stream(...).await;
if outcome.cancelled {
    cancelled = true;
    break;              // ← 先跳出去了
}
// 累积这一轮的产出（工具循环的中间轮通常没有正文，只有 tool_calls）
final_content.push_str(&outcome.content);   // ← 取消时根本走不到这里
```

`final_content` 永远是空的，而 `persist_turn` 的规则是
**「空正文的 ok / cancelled 轮不落库」**（只有 error 轮即使空正文也要落），
于是这一轮被静默丢弃。

修法不是「在取消分支里补一句 push」——那样下次改这段代码的人
（包括我自己）还会写反。改成把**累积和判断合成一个函数**，
顺序固化在内部：

```rust
match turn.absorb(&outcome) {   // absorb 内部：先 push，再判断
    RoundFlow::Cancelled => { cancelled = true; break; }
    RoundFlow::Failed(e) => { terminal_error = Some(e); break; }
    RoundFlow::Done      => { completed = true; break; }
    RoundFlow::Tools     => {}
}
```

配套 4 条单测钉住这个不变式（取消 / 出错 / 多轮拼接 / usage 与 finish_reason），
其中 `a_cancelled_round_still_contributes_what_already_streamed`
就是照着这个 bug 写的 —— **它在这条 bug 存在时必然失败**。

> 值得记下来的是：这个 bug 是**纯逻辑顺序错误**，`clippy` 不会警告、
> 类型系统看不出来、而它的「用户可见症状」要等到用户重开应用才出现。
> 这就是「实测」不可替代的地方。

### 4. 抓到的第二个问题：启动失败 = 一个全透明的窗口

排查上面那个 bug 的过程中，我一度把应用卡在了「启动不起来」的状态，
而它的表现是：**窗口对象存在、置顶、`IsWindowVisible` 为真，但整页全透明**，
没有任何报错。原因是 `.app` 的初始 `opacity: 0`，只有 `data-phase` 切到 `shown`
才显示；而 `boot()` 里任何一步抛异常都会让 `showWindow()` / `playEnter()` 不再执行。

修法有两层，都做在 `src/main.tsx`：

1. `boot()` 外面包一层 `start()`，任何异常都调 `showBootFailure()` ——
   它把 phase 直接设成 `shown`，并用最朴素的 DOM 把错误画到窗口上
   （不依赖 React，此时它可能压根没挂载成功）；
2. `window.addEventListener("error" / "unhandledrejection")` 也接到同一个出口 ——
   React 在**渲染期**抛异常时会卸载整棵树，那一步走不到 `boot()` 的 catch 里。

> **这两个钩子必须写在模块文件里，不能写在 `index.html` 的内联 `<script>` 里**：
> CSP 是 `script-src 'self'`。我一开始就是写在 `index.html` 里的，
> 结果不只是那个钩子没生效 —— **整个页面的脚本都被拦掉了**（见下一条），
> 表现同样是那个透明窗口。`index.html` 现在保持干净。

### 5. 两个构建 / 配置陷阱（都踩过，都记在 README 里）

| 陷阱 | 现象 | 结论 |
|---|---|---|
| 用裸 `cargo build --release` 打包 | 进程起来、WebView2 也在跑，但前端**一个 IPC 都不发**，窗口停在初始态；改 `lib.rs` / `build.rs` 的 mtime 都不管用 | 前端资源是 `tauri-build` + `generate_context!` 两步嵌进去的，**只有 `npm run tauri:build` 能打出能跑的二进制**；`cargo build` 只用于检查与单测 |
| `index.html` 里写内联 `<script>` | 整个页面不工作（不是「少个功能」） | CSP `script-src 'self'`；需要在渲染前装的钩子一律写进 `src/main.tsx` |

判断「到底有没有嵌进去」有一个笨但可靠的办法：**在 Rust 侧的命令里临时
`eprintln!`，把 stderr 重定向到文件**。一个都不打印 = JS 根本没跑。

### 7. 顺带修掉的一处静默失败

`ApprovalScope::Always` 分支里原本写的是 `let _ = config.update(...)`。

现场没有任何线索。现在改成把错误打出来：

```rust
if let Err(e) = config.update(...) {
    eprintln!("记住「永久允许」（工具 {}）失败：{e}", tool.name);
}
```

## 十五、第六轮：按参考清单补齐功能（P0 批次）

对照参考项目（Zhima / ChatFloat）的 12 大模块清单逐项核实之后，fuyu 的**核心三块
（对话 / 模型 / 桌面集成）已经在位**，缺口按「能不能纯本地做」分了三档。这一轮先做
P0：10 项全部是纯本地、可测、可验证的。**不做**需要服务端账号体系的第十二类
（登录 / 会员 / 云同步 / 社区市场）—— 那与这个项目「本地优先、无账号、密钥不出本机」
的定位直接冲突，要做应该是另一个后端项目。

### 1. 一键复制（回复 + 代码块）

三处设计：

- **走 Rust 的 `arboard`，不用 `navigator.clipboard`**。浏览器的剪贴板 API 要求
  「安全上下文 + 用户手势」，而悬浮窗会被程序化 show/hide、还会失焦自动隐藏 ——
  这类场景下它会**静默失败**。走 Rust 只有一种失败模式（剪贴板被别的程序占住），
  而且失败能被如实报出来。
- **命令是 `async` 的**：Tauri 里非 async 命令跑在主线程，而 Windows 剪贴板在别的
  程序占着时会重试等待 —— 那会把界面一起卡住。
- **失败必须看得见**：`copyText()` 把失败变成返回值而不是异常（异常很容易在调用点
  被 `void copy()` 吞掉），按钮文字当场变成「复制失败」并推一条提示。
  复制最怕的不是复制不了，而是**看起来复制成功了、粘出来还是上一次的内容**。

代码块的复制按钮在头部固定占位（没有语言标注也留一行），否则按钮位置会在代码块之间
上下跳，很难点。

### 2. 模型收藏星标

`ModelEntry::favorite` 这个字段**从第一版就在数据结构里，却一直没有界面能改它** ——
典型的「数据模型准备好了、产品功能没接上」。这一轮补上：

- Rust 侧 `set_model_favorite`，变更逻辑抽成纯函数 `apply_model_favorite` 以便单测
  （命令要 `State`，构造不出来）；
- 收藏**只影响展示顺序**，不动默认模型：星标一个模型不等于要把当前会话切过去，
  这两件事混在一起会让「随手点个星星」意外改变正在用的模型；
- 原生 `<select>` 里放不下星标按钮，所以下拉里只用 `★` 前缀 + 排序表达，
  真正的开关在「设置 → 模型」的模型标签上。

### 3. 窗口透明度与正文字号

- 透明度**只作用在背景**上：把「颜色」和「透明度」拆成两段 CSS 变量
  （`--bg-rgb` / `--bg-alpha` × `--win-opacity`），文字始终保持不透明 ——
  否则「调透明」会变成「调得看不清」。
  `--bg-elevated`（设置面板）刻意不参与：不管窗口调多透明，设置面板都必须清晰，
  否则用户没办法把它调回来。
- **硬边界在后端**：`MIN_WINDOW_OPACITY = 0.35`，字号 11~18px，`NaN` 直接报错。
  理由很具体：这个值会被写进 CSS 变量，`0` 的后果是**窗口全透明** ——
  用户看不见界面，自然也点不到设置，只能手改配置文件。一个滑块能让应用无法使用，
  是设计缺陷而不是「用户自己的选择」。
- 字号挂在 `body` 上：气泡、输入框这些「要读的文字」本来就继承它，而按钮/标签
  自己写了 px 字号（那是控件，不该跟着放大）。这样「字号」只影响阅读，
  不会把整个界面撑变形。
- 拖动时**即时预览**：`update_settings` 每条命令带一次 fsync，所以滑块是停手 350ms
  才提交的；不预览的话用户拖动时界面毫无变化，会以为滑块坏了。

### 4. 实测过程中顺出来的一批「测试工具本身的坑」

这一轮的验证过程比功能本身更值得记：

| 现象 | 真正的原因 |
|---|---|
| 截出来的窗口画面残缺、而且窗口再也移不动（`SetWindowPos` 直接返回 0） | **我自己的驱动脚本**在 `ShowWindow` + `SetWindowPos(HWND_TOPMOST)` + `SetForegroundWindow`。而这个应用本来就是 `alwaysOnTop` + 自绘标题栏，自己会显示、自己就在最上层 —— 驱动**只该读数，不该动窗口** |
| 点一下标题栏按钮，窗口就消失了 | `hideOnBlur = true`（默认）的正常行为：脚本进程一退出，控制台拿回焦点，应用失焦就隐藏。**这正是 README 里写的「测之前先关掉失焦自动隐藏」**，是我自己忘了 |
| 启动后窗口不可见（偶发） | 真 bug，已修：配置还没加载时 `hideOnBlur` 只能按默认值 `true` 取，于是**用户明明关掉了失焦隐藏，启动头一两百毫秒里它仍然生效**。症状是「窗口一闪就没了」，只在启动瞬间偶发。修法是等 `config.loaded` 为真再注册监听 |
| 组件测试里「空内容」却渲染出了按钮 | **JSX 属性里的 `\n` 是字面量**，不是换行：`text="   \n "` 拿到的是带反斜杠的字符串，`trim()` 之后长度还有 2 |
| 组件测试里 `setState` 之后组件读到的仍是初始值 | **SSR 下 zustand 走 `getServerSnapshot`**，拿到的永远是初始状态。要测读 store 的组件，必须把 store 整个 mock 成普通函数 |
| 怀疑自己的 CSS 把窗口背景写坏了 | 用 **Edge 无头模式**加载一份最小 HTML 直接验证那段 CSS（`rgb(var(--bg-rgb) / calc(...))` 在 Chromium 里是合法的）—— 比每次改完都重新打包应用快得多 |

一句话总结这一轮的教训：**当「实测」开始给出矛盾结论时，先怀疑测量工具，再怀疑被测对象。**
上面六条里有五条是工具的错，只有一条（启动竞态）是真 bug —— 如果当时直接去改产品代码，
就会把好代码改坏。

### 5. 这一轮的验证方式

| 层 | 手段 |
|---|---|
| 剪贴板真伪 | Rust 测试**真读写真系统剪贴板**（先存下用户原内容，测完还原；拿不到剪贴板时跳过并打印原因） |

## 十六、第六轮（续）：角色预设

### 1. 一个设计选择：会话存 `role_id`，不抄提示词

最省事的做法是「选了角色就把它的提示词写进 `conversations.system_prompt`」——
那个字段本来就存在。但那样有两个后果：

- 用户改了角色的措辞，**已有会话不会跟着变**（看起来像「改了没用」）；
- 界面没法显示「这个会话现在是哪个角色」，只能拿提示词去反查 ——
  改一个标点就匹配不上了。

所以加了 v13 迁移：`conversations.role_id`（可空，NULL = 回落到全局系统提示词）。
代价是一次迁移和两个查询的改动，换来的是「角色可改、可显示、可切换」。

**解析发生在发送那一刻**（`resolveRolePrompt`），不是建会话那一刻：
用户改了措辞，下一个问题就用新的。

### 2. 优先级只有一条，但要写清楚

```
会话绑定的人设  →  全局系统提示词（设置 → 对话）  →  没有
```

找不到角色时（用户删了它）**安静地回落到全局**，不报错：那是用户自己的操作，
不该把他卡在一个「发不出去」的状态里。前端返回 `null` 而不是空串 ——
空串在后端会被当成「用户显式要求没有系统提示词」，而我们要的是「没指定」。

### 3. 校验放在后端

`sanitize_roles` 拒绝：空 id / 空名字 / 空提示词 / 重复 id / 超过 50 个 /
提示词超过 4000 字。理由和「永久允许」白名单一样 —— 这些值会被原样拼进
每一次请求，**前端拦一遍不够**（命令可以被直接调用），而且坏数据写进配置之后
用户很难自己发现。上限也不是洁癖：几百个角色会让每个请求白白多花几千 token。

内置模板**可改不可删**：删了就找不回来，用户只能手工补一段他自己都不记得的文本。

### 4. 界面上只做两件事

- 输入框上方的下拉：按**会话**切换人设（不是全局开关）——
  「翻译一段话」和「帮我改代码」通常发生在不同会话里，做成全局开关会让人来回改；
  没有活动会话时下拉是禁用的，并说明原因（人设是挂在会话上的，此时改了没地方存）。
- 设置 → 对话：角色编辑器（改名 / 改提示词 / 新增 / 删除自建角色）。
  名字输入框平时看起来像一行标题，**聚焦才显出是输入框** ——
  四个角色的编辑器里全是方框会非常吵。

### 5. 验证

| 层 | 手段 |
|---|---|
| 解析规则 | 8 条前端单测：找不到 / 空提示词 / 改了立刻生效 / id 不重复 |
| 校验规则 | 6 条 Rust 单测：空值 / 重复 id / 数量与长度上限 / **内置模板自己能过校验**（否则「重置设置」会把配置写成非法状态） |
| 持久化 | 2 条 Rust 单测：角色记得住也能清掉、**列表里也带 role_id**（只在 `get_conversation` 里有的话，列表驱动的界面会显示成「无角色」） |
| 不该动的别动 | 换人设**不改 `updated_at`** —— 否则一个旧会话会因为「改了个人设」跳到列表最前面，用户会以为来了新消息 |
| 迁移 | 真机确认 `user_version` 11→…→13、`conversations.role_id` 存在 |
| 配置 | 真机确认 4 个内置角色写进了 `providers.json` |

## 十七、第六轮（续）：备份导出与导入

### 1. 为什么不是「把数据库文件复制一份」

最省事的备份就是把 `floatai.db` 拷走。但那样有个致命问题：**换个版本就废了**。
库结构在演进（这一轮就加了 v13），用户拿着一个 v9 的 `.db` 回来，应用要么
认不出来、要么按新结构去读旧数据 —— 而备份的意义恰恰是「以后还能用」。

所以导出的是**应用自己定义的 JSON 格式**，带两样东西：

```json
{ "app": "fuyu", "version": 1, "exportedAt": 1791…, "conversations": [ … ] }
```

- `app` 标记：挡住「随便选了个 JSON 文件」；
- `version`：将来改格式时能给出「**请升级应用**」这种明确提示，
  而不是一个 JSON 解析错误。

三类错误分开报，因为它们对应完全不同的处置方式：文件不对（重新选）/
版本更新（升级应用）/ 文件太大（说清上限，而不是把内存吃光）。

### 2. 导入**只新增，绝不覆盖**

导入最常见的场景是「换机器 / 重装后恢复」，那时用户手上的库是空的；
而在非空库上做「合并 / 覆盖」，一次手滑就能毁掉正在用的历史。
所以按 id 去重：已存在的会话整个跳过，并在结果里如实报告「新增 N、跳过 M」。

整份导入放在**一个事务**里：中途失败一条都不落，不会留下半份数据让用户
反复重试还越导越乱。想真的重置，用户有「清空全部历史」这个显式入口。

### 3. 图片原样带走

导出包含图片的 data URL。理由：备份悄悄丢一部分数据，比文件大要糟得多 ——
用户要的是「换台机器还能接着用」，而不是「一份看起来完整的残缺副本」。
代价是带大量图片时会很大，所以界面会显示文件体积，导入侧也有 256 MB 的硬上限。

顺带一个坑：导出**不能**复用 `list_messages` —— 那个为了省内存只给最近
`IMAGE_HISTORY_LIMIT` 条消息加载图片，直接用会导出一份「近期有图、早期没图」
的备份，而且不报错。

### 4. 不引入额外插件：导出写目录、导入选文件

原生「另存为 / 打开」对话框需要 `tauri-plugin-dialog`（外加权限声明）。这一步
选择：

- **导出**：由后端写到 `<应用数据目录>/exports/fuyu-export-<时间戳>.json`，
  把完整路径显示给用户并支持一键复制；
- **导入**：WebView 原生的 `<input type=file>`（能可靠拿到文件内容，
  而真实路径在 WebView 里拿不到）。

好处是零新依赖、路径完全可预测；代价是导出不能自选位置。这是**有意的取舍**，
下一步接对话框插件时，界面不用改。

### 5. 验证

| 层 | 手段 |
|---|---|
| 格式校验 | 7 条单测：合法解析 / 缺字段回退 / 别人的 JSON / 随机 JSON / 版本更新提示升级 / 超体积 / 空备份 |
| 导出落盘 | 3 条单测：文件确实进 `exports/`、**写出来还能被自己解析回去**（否则「导出了却导不回去」）、目录不存在时自建、连点两次不互相覆盖 |
| 导出→导入往返 | 1 条单测（真开临时库）：会话标题/角色/消息条数/推理内容/token 都还原，**导进同一个库不产生重复**，且**导入的消息能被全文搜索搜到**（触发器要对导入生效，否则「恢复了但搜不到」） |
| 手改过的备份 | 1 条单测：标题为空 → 补默认标题（否则会话在列表里没有名字） |
| 迁移 | 真机确认 `user_version = 13` |

## 十八、第六轮（续）：开机自启、数据管理、诊断信息

### 1. 开机自启：插件只在 Rust 侧用

官方 `tauri-plugin-autostart` 有 JS API，但前端一个都没用 —— 前端调的是我们自己
的两个命令（`set_autostart` / `autostart_status`）。好处是：不必给前端加依赖，
也不必在 `capabilities` 里放开插件权限。**少一层权限面，就少一处可能配错的地方。**

两个刻意的决定：

- **先改系统、再写配置**。反过来的话，注册表写失败会留下一份「配置说要开、
  实际没开」的谎报，而用户下次只能在任务管理器里困惑。
- 界面上那个勾显示的是 `autostart_status` 读回来的**系统真实状态**，
  不是配置里的值。用户完全可能用任务管理器把自启项删掉 ——
  显示配置值就会出现「勾还打着、开机却没启动」，而用户不知道去哪儿查。

### 2. `--minimized`：一个只有开机才会暴露的坑

自启项带 `--minimized`，前端启动流程里问一次 `started_minimized()`，是的话
**不**显示窗口。不加这条的话，每次开机都会有一个置顶悬浮窗蹦到屏幕中间挡住视线 ——
而这个问题的恶心之处在于：**开发时手动启动永远复现不了**。

解析逻辑 `is_minimized_launch` 抽成接收迭代器的纯函数，专门为了能在不碰真实
`std::env::args()` 的情况下单测：`--minimized-foo` 不能被误判、空参数列表不能炸、
开关出现在命令行任何位置都要认出来。

真机验证（这是本轮最干净的一条证据）：

| 启动方式 | 结果 |
|---|---|
| 正常启动 | 窗口句柄存在，`IsWindowVisible = true` ✓ |
| `floatai.exe --minimized` | 窗口句柄存在，`IsWindowVisible = **false**`，进程仍活着 ✓ |
| 验证后检查注册表 | `HKCU\...\Run` 里**没有** floatai 项 ✓（不能给用户留意外的自启项） |

### 3. 数据管理：为什么「重置设置」保留服务商

API Key 存在系统凭据管理器里，是按 provider id 挂的。如果把服务商列表也重置掉，
那些密钥就变成**没有任何界面能看到的孤儿**：用户以为「重置设置」只是恢复默认外观，
结果密钥永远留在系统里，删都删不掉。所以 `reset_keeping_providers` 只保留
「服务商列表 + 默认服务商 + 默认模型」，其余（外观、提示词、人设、工具白名单、
代理、温度、上下文预算）一律回默认。

「删除全部密钥」做成**独立动作**，不藏在重置里：它不可撤销，而用户想
「把密钥从这台机器上撤掉」时不该被迫连外观设置一起重来。

### 4. 诊断信息：以前只能靠命令行看 stderr

出错时界面上只有一条提示，用户一刷新就没了，想反馈也说不清；唯一能看到细节的地方
（从命令行启动 exe 看 stderr）对普通用户等于不存在。现在：

- `LogBuffer` 是一个**有界**（200 条）环形日志，超了丢最旧的。
  诊断功能绝不能自己变成内存泄漏源。
- 记录点选在**终态那一处**（`run_stream` 里判定 `terminal_error` 的地方）：
  无论错误来自建连、SSE 解析还是「工具轮次用满」，都只经过这里一次。
- **只记服务商 / 模型 / 错误码与信息**，绝不记 API Key、请求正文、消息内容 ——
  诊断信息是要给用户复制出去给人看的，它天然是一条外发通道。
- 界面把环境与日志拼成一段可直接复制的文本（`formatDiagnostics`，6 条单测，
  其中包括「时间补零」「按量级选单位」「有错误时逐条列出」这些会直接影响可读性的点）。

### 5. 顺手修掉一条不稳定测试

`cancelling_stops_the_stream_and_keeps_partial_content` 原来用「两片之间隔 3ms」
+「睡 25ms 再取消」：**取消和第一片到达在赛跑**。并行跑测试、机器一忙就会随机失败，
而且失败信息看起来像产品 bug（`已到达的内容必须保留，实际为 ""`）。

修法不是把断言放宽，而是把两个时间拉开：两片间隔 500ms、睡 150ms 再取消。
两边都留出足够余量之后，反而可以把断言**收紧**成「正好只收到第一片」——
这才是这条测试本来想表达的东西。连跑 3 遍全量 217 条，稳定通过。

## 十九、第六轮（续）：用量趋势与费用估算

### 1. 核心设计只有一条：估不出来就说估不出来

价格表是内置的，**一定会过时**（各家一年能改好几次），而且用户完全可以自己加一个
从没见过的模型。所以：

- 表里没有的模型返回 `None`，命令把它列进 `unpricedModels`，界面显示
  「以下模型不在价格表里、未计入费用」；
- 悄悄按 0 计入会给出一个**看起来很确定的错数字** —— 那比不给数字更糟，
  因为用户会拿它去对账。

配套的两个诚实细节：小于一分钱显示 `<¥0.01` 而不是 `¥0`（后者看起来像没花钱）；
每一天还带一个 `hasUnpriced` 标记，因为「这天有一部分没计价」和「这天花了 0 元」
在图上长得一样。

### 2. 价格表最容易写错的地方是匹配顺序

匹配用「模型 key 的小写子串」，**从具体到宽泛**依次判断。
`deepseek-reasoner` 必须排在 `deepseek` 前面 —— 推理模型贵好几倍，
顺序写反会让估算**偏低**且没有任何提示。有一条单测专门钉这个：

```rust
assert!(reasoner.input_per_million > chat.input_per_million);
```

### 3. 聚合的粒度是「天 + 模型」，不能先合并再计价

不同模型单价不同，按天先把 token 加起来再乘一个价是错的。所以 SQL 直接
`GROUP BY day, provider_id, model_key`，估算逐行做、再按天汇总。

SQL 里两个过滤条件都是必要的，而且**都不能只看「是不是助手消息」**：

```sql
WHERE role = 'assistant'
  AND created_at >= ?1
  AND (COALESCE(input_tokens, 0) + COALESCE(output_tokens, 0)) > 0
```

- 用户消息没有 token，放进来会造出一堆「模型名为空」的行，
  然后被费用估算列成「认不出来的模型」—— 纯噪音；
- 被取消 / 失败的轮次通常没有 usage，它们也不该算钱。

日期按**本地时间**分组（`date(created_at/1000,'unixepoch','localtime')`）：
用户看的是「我昨天花了多少」，不是 UTC 的昨天。

### 4. 验证：这条 SQL 必须拿真 SQLite 验

单测里的消息都是「刚刚插入的」，全落在同一天 —— **多天分组根本没被覆盖**。
所以另外用一个探针脚本往真实库里塞了 3 天、6 条消息（含一个未计价模型、
一条被取消的轮次、一条用户消息），跑**与 Rust 侧完全相同的那条 SQL**：

| 断言 | 结果 |
|---|---|
| 分组行数（3 天 → 今天 2 行 + 昨天 + 前天 = 4） | ✓ |
| 天数 | ✓ 3 |
| 输入 / 输出 token 合计 | ✓ 1,700,000 / 1,600,000 |
| 计入的回答数（取消轮与用户消息都不算） | ✓ 4 |
| 同一天两个模型**分开**成两行 | ✓ |
| 最旧一天在前（升序，供上层反转） | ✓ |
| 费用抽查（100 万输入 × 2 元） | ✓ ¥2.00 |
| 未计价模型仍参与 token 统计 | ✓ |

最后一条也很重要：认不出价格的模型**仍然要算进 token**，
否则用户会以为「这天没用过」—— 我们只是不算钱，不是没看见。

### 5. 前端两个「画出来的图不对但不报错」的坑

`src/lib/usage.ts` 单独成文件并配 16 条测试，就是为了这两条：

- **除零**：新装的用户所有天都是 0，`0/0` 得到 `NaN%`，React 会老老实实
  把它写进 `style`（柱子消失或宽度异常，不报任何错）。
- **非有限值**：`Infinity` 若只做 `Math.min(100, …)` 会得到**满格** ——
  一个坏数据反而画成「这天用量最大」。所以先 `Number.isFinite` 判掉。
- 另外「有量但很小」的那天至少给 1.5% 宽度，否则看起来像这天没用量。

## 二十、第六轮（收尾）：文本文件附件

### 1. 校验分三层，缺一不可

「拖个文件进来读进上下文」看起来是个十行功能，但真实用户会拖进来的东西是：

| 输入 | 只查扩展名 | 只查字节 | 三层都查 |
|---|---|---|---|
| `notes.md` | ✅ | ✅ | ✅ |
| 把 `.exe` 改名成 `.txt` | ❌ 放行 | ✅ 挡住（含 NUL） | ✅ |
| GBK 编码的 `.txt` | ❌ 放行 | ✅ 放行 | ✅ 挡住（非法 UTF-8） |
| 20 MB 的 `app.log` | ✅ | ✅ | ✅ 挡住（大小上限） |

所以顺序是：**扩展名白名单 → 字节像不像二进制 → 是不是合法 UTF-8 → 大小与个数**。

- 白名单而不是黑名单：黑名单永远列不全（`.dat` / `.bin` / `.db`…）。
- 二进制判据用两条宽进严出的：出现 NUL（UTF-8 文本不可能有），或控制字符
  比例超过 10%。宁可放过，也不误杀中文与 emoji。
- `TextDecoder("utf-8", { fatal: true })` 而不是默认的「替换成 U+FFFD」：
  默认行为会把一个 GBK 文件变成满屏问号发给模型，用户完全不知道发生了什么。

### 2. 围栏长度必须跟着内容走

文件内容本身可能就是一篇 Markdown（自带 ``` 围栏）。固定用三个反引号会被内容
**提前闭合**：后面的内容跑到围栏外面，被当成对话正文 —— 于是「附加了一个文件」
变成「模型收到两段格式错乱的东西」，而且两边都不报错。

所以围栏取「内容里最长连续反引号 + 1」，至少 3（`fenceFor`）。
有一条测试专门喂进一篇自带 ``` 的文档来钉这个行为。

### 3. 两个顺手做对的细节

- 附件拼在提问**前面**（先材料后问题，注意力顺序更自然；而且上下文预算不够时
  是从最旧开始丢，先丢附件也不会丢用户的提问）。
- 附件是拼进正文的：这样它天然进历史、天然被持久化，**不需要给数据库加字段**。
- 多个文件**逐个独立判断**：一次拖五个、其中混着 `.exe` 是常事，
  「一个不合格就整批放弃」会让用户以为功能坏了。

### 4. 验证

| 层 | 手段 |
|---|---|
| 校验规则 | 25 条前端单测：扩展名（含无扩展名 / `.gitignore` / 结尾是点）、NUL 与高比例控制字符判二进制、少量控制字符不误杀、GBK 非法 UTF-8、大小与个数与合计（**边界两侧都验**） |
| 围栏 | 3 条：普通内容用 ```、内容自带 ``` 时加长、`attachmentBlock` 的收尾确实是那条更长的围栏 |
| 拼装 | 4 条：无附件时原文、附件在前、只有附件不留空段落、多个附件都带上 |
| 构建 | 真机 `npm run tauri:build` + 启动可见（6.24 MB exe / 2.22 MB 安装包） |

## 二十一、第七轮：代码高亮与数学公式

### 1. 代码高亮：保住「不注入 HTML」这条不变式

`Markdown.tsx` 开头原本就写着一句话：「全程不碰 `dangerouslySetInnerHTML`：
模型输出是不可信输入」。而**几乎所有**现成方案都违反它：

| 方案 | 输出 | 能直接用吗 |
|---|---|---|
| `hljs.highlight()` | HTML 字符串 | ✗ 必须注入 |
| Prism `highlight()` | HTML 字符串 | ✗ 必须注入 |
| shiki `codeToHtml()` | HTML 字符串 | ✗ 必须注入 |
| **lowlight** | **hast 语法树** | ✓ 映射成 React 元素即可 |

所以选 lowlight：它输出的是 `{type:"element", tagName:"span",
properties:{className:["hljs-keyword"]}, children:[…]}` 这样的树。
我们把它转成自己的最小结构（`toHighlightNodes`），再映射成 `<span>` ——
**代码高亮一次都没有注入 HTML**，原来那句注释依然成立。

三个踩到的细节：

- **未知语言会抛异常**（`Unknown language: ... is not registered`）。必须先
  `registered()` 判断，否则模型随手写个 ```` ```代码 ```` 就能让整个气泡崩掉。
- **别名是 lowlight 自己注册的**（`rs` / `ts` / `py` / `sh` / `yml` / `cs` …，
  甚至 `c++`）。所以 `normalizeLanguage` 的契约是「返回一个 lowlight 能接受的名字」，
  而不是「返回规范名」—— 一开始我按规范名写了断言，红了一片，是**测试写错了**。
- **不做自动语言探测**。中文正文里猜语言经常猜错，而「猜错的配色」比没有配色更难看懂。
  没写语言就老老实实按纯文本渲染。

### 2. KaTeX：全项目唯一一处窄口子，三重守卫

公式没法用 React 元素表达（KaTeX 只有 HTML 输出），所以这里**必须**破例。
破例的做法是把它做成一个**有守卫、会降级**的窄口子：

1. `trust: false`（显式写出并单测钉死）—— 它挡掉 `\href` / `\url` /
   `\includegraphics` / `\html*` 这一整类「公式里能塞链接和属性」的能力；
2. `looksSafe()` 兜底：即便 KaTeX 出漏洞或将来换实现，输出里出现
   `<script>` / 事件处理器 / 危险协议就**退回显示源码**；
3. 任何失败（渲染异常、兜底不过、公式超长）都降级成 `$x^2$` 的**源码文本** ——
   用户至少能看见这里原本有个公式，而不是一片空白。

### 3. `looksSafe` 的一个真实教训：别搜子串

第一版里我写了 `javascript:` 就判危险，测试立刻红了 —— 但**红得有道理**：
KaTeX 在 `trust:false` 下会把 `\href{javascript:...}` 渲染成**红色的错误文本**，
于是 `javascript:` 会以**转义文本**的形式正常出现在输出里。
按子串判会把这种完全无害的情况判成危险（用户写 `$\text{javascript: 是协议}$` 时
公式会莫名退回源码）。

正确的判据是**属性上下文**：

```js
/(?:href|src|xlink:href)\s*=\s*["']?\s*(?:javascript|vbscript|data:text\/html)/i
```

同理 `<a` 也不能直接搜 —— KaTeX 的 MathML 输出里有个 `<annotation>` 标签。
这两条都写成了测试，防止以后有人「顺手加一条黑名单」。

### 4. 解析器里那个更难发现的 bug：两套判据不一致

行内公式 `$...$` 的判据必须够严，否则 `价格是 $5 和 $10` 会变成公式。
我写了带前后视的正则来拒绝它，测试却显示**它还是变成了公式**。

原因不在正则：`String.split` 不匹配时，整串会作为一个 **text 片段**返回，
而我的分类代码是这样的：

```ts
if (part.length > 2 && part.startsWith("$") && part.endsWith("$")) {  // ✗
  tokens.push({ kind: "math", value: part.slice(1, -1) });
}
```

正则**正确地拒绝了**，分类代码又用 `startsWith/endsWith` 把它**收了回来** ——
拒绝白拒了。修法是让分类用与正则**同源的锚定判据**（`MATH_PART` / `CODE_PART` /
`BOLD_PART`）。教训：一个值的合法性如果由两处判断，两处必须是同一套规则。

### 5. 验证：不靠眼睛，也不需要 OCR

这个模型读不了图片，`--dump-dom` 在新版无头模式下又拿不到输出。所以做了个
**把结果编码成像素**的探针：

- `tools/render-preview.tsx` 用**真实组件**渲染出一个 HTML 页面，
  里面有一段脚本把 8 项检查（KaTeX 结构 / display 模式 / **字体真的生效**
  / 高亮 token / 深色主题 / 价格没被误判 / 没走降级分支 …）画成 24×24 的
  绿/红方块；
- `tools/check-preview.py` 读截图里那几个像素，逐项报通过/失败；
- 另外直接在像素里找 `--syntax-*` 的**精确颜色**，确认高亮配色真的画上去了。

跑出来的结果：**8/8 检查通过**，keyword / string / number / meta 四种 token
配色都在画面上找到了对应像素（37 / 95 / 12 / 40 个）。

顺带一个「又一次是测量工具的错」：第一次跑时 `number` 是 0 命中，
看着像配色没生效 —— 其实是**样例代码里根本没有数字字面量**。
补上 `let scale = 42;` 之后立刻命中。这件事已经写进 `check-preview.py` 的注释里，
免得以后有人去「修」产品代码。

### 6. 体积代价

主包从 283 KB 涨到 722 KB（gzip 227 KB）：37 种语言的 highlight.js 与 KaTeX
都是**静态**引入的 —— 高亮和公式在聊天里出现得太频繁，懒加载只会让每条消息
先闪一下再上色。而 mermaid（671 KB / gzip 165 KB）做成**独立 chunk**：
只有消息里真的出现 ` ```mermaid ` 才去下载。桌面应用读本地文件，
这个代价换「代码有配色、公式能排版、图表能画」是划算的。

## 二十二、第七轮（续）：mermaid 图表

### 1. 又一个必须注入 HTML 的地方

mermaid 输出 **SVG 字符串**（布局要它自己算，没有节点树 API），所以这是第二处、
也是最后一处注入点。做法与公式一致，并且**共用同一个守卫**
（`lib/safe-html.ts` 的 `looksSafe`，从 `lib/math.ts` 里抽出来共用）：

1. `securityLevel: "strict"`（显式写出并单测钉死）—— mermaid 用它自带的
   DOMPurify 清洗生成的 SVG，禁用点击交互与脚本；
2. 外面再过一遍 `looksSafe()`；
3. 画不出来就退回 ` ```mermaid ` 源码块（**仍然带复制按钮**），不留空白。

`startOnLoad` 也必须是 `false`：让它自己扫描页面的话，用户消息里恰好长得像
mermaid 的普通文本也会被拿去渲染。这条也写成了测试。

### 2. 主题切换：mermaid 会把主题缓存起来

mermaid 的主题是在 `initialize()` 时定的，之后 `render()` 一直用它。所以切到深色
主题后**新画的图仍然是浅色**。两处要配合：

- `renderMermaid` 记住上次初始化的主题，主题变了就重新 `initialize`；
- 组件用 `MutationObserver` 盯 `<html data-theme>`（`applyTheme` 改的是这个属性，
  React 不会因此重渲染），主题一变就重画。

### 3. 验证：SSR 看不到 useEffect，于是加了客户端渲染验证

`tools/render-preview.tsx` 走的是服务端渲染 —— 而 `useEffect` 在 SSR 里**不执行**，
mermaid 这种异步 + 依赖 DOM 的渲染在那里永远看不到。所以补了第二条路：

- `tools/preview-client.tsx` 用 `createRoot` 把组件**真的挂载到浏览器里**；
- `tools/build-preview.mjs` + `tools/vite.preview.config.ts` 把它打成一个
  自包含的 IIFE（React + mermaid + 应用 CSS 都打进去，`file://` 直接能开）；
- 挂载后组件自己轮询等 mermaid 画完，再把 11 项检查编码成绿/红方块。

结果（`--set=client`）：**11/11 通过**，其中 mermaid 相关的 6 项全过 ——
svg 画出来了、图里有文字节点、没卡在加载态、**深色主题下也画了**、
svg 里没有脚本与事件处理器、两张图都画了。

## 二十三、第八轮：Office 文档解析（docx / xlsx / pptx）

### 1. 为什么解析放在 Rust 侧

docx / xlsx / pptx 都是 **ZIP + 一堆 XML**。浏览器里解要引一堆 JS 库（体积按 MB 计），
而 Rust 这边 `zip` + `quick-xml` 就够了。更重要的是**上限能在后端强制执行** ——
前端的限制拦不住直接调命令的人，而这里要挡的是 zip bomb。

做法上刻意**不**还原版式（表格样式、图片、页眉页脚一律丢）：目标是「把内容喂给模型」，
不是「渲染一份文档」。

三条安全约束：

| 约束 | 值 | 挡什么 |
|---|---|---|
| 条目数 | 2000 | 塞几万个条目的压缩包 |
| 解压后总大小 | 64 MB | **zip bomb**（几百 MB 能膨胀成几十 GB） |
| 正文字符数 | 256 KB | 一个几 MB 的表格把上下文预算一次吃光 |

第三条超限时**明确标注「已截断到 N 字」**，而不是悄悄丢 —— 悄悄丢会让模型（和用户）
都以为看到的是全部。

### 2. 一个静默丢内容的坑：quick-xml 0.42 的 `GeneralRef`

第一版跑出来是这样：

```
【数据】
	3	5.5
	12	2.25
```

**数字都在，文字整列没了。** 看起来像「读到了，但内容不对」。

原因：openpyxl 写出来的字符串是**内联**的（`t="inlineStr"`）且用**数字字符引用**
（`&#21517;&#31216;`）。而 quick-xml 0.42 起把实体引用**单独报成
`Event::GeneralRef`**，不再混在 `Event::Text` 里 —— 只处理 Text 的代码就会把这些
文字整段漏掉，而且**一声不响**。

修法是两种事件都收（`ref_text()` 处理数字引用、五个预定义实体，外加导出文档里常见的
`&nbsp;`；未定义实体原样保留而不是丢掉）。顺带把同一层里另外两个
`if let Ok(...)` 式的静默分支也都改成会出声的形式。

这条现在有专门的回归测试（`inline_strings_with_numeric_references_are_decoded`）。

定位过程本身也值得一提：先怀疑 `unescape` 失败、又怀疑编码，都不是；最后**把事件流
逐个打出来**才看到 `GeneralRef`。当「读到了但内容不对」时，先看原始事件流，
比继续在解析逻辑里猜要快得多。

### 3. 一个被自己的测试逼出来的 bug

`canAddAttachment` 同时管「单文件上限」和「合计上限」。给 Office 文档接入时，
我在**解析之前**用**文件大小**（可达 9 MB）去调它 —— 于是 512 KB 的合计上限
直接把任何稍大的文档拒了，功能等于废掉。

是边界断言把它揪出来的（`canAddDocument([], "边界.docx", MAX_DOCUMENT_BYTES)`）。
修法是把两件事拆开：

- 解析前：`canAddDocument` 只判**个数 / 类型 / 单文件大小**；
- 解析后：用**提取出来的正文大小**再过一次合计上限（正文本来就被后端截到 256 KB）。

教训与解析器那条一致：**一个值的合法性如果由两处判断，两处必须是同一套规则**；
反过来，两件不同的事（文件大小 vs 正文大小）也不该硬塞进同一个判断里。

### 4. 离线环境的两个连带发现

1. **网络中断时的依赖裁剪**：`cargo build` 报 `Could not resolve host: static.crates.io`，
   缺的是 `zstd-sys`。而 Office 文件用的本来就是 deflate，于是把 zip 改成
   `default-features = false, features = ["deflate"]` —— 既去掉了用不上的 C 依赖，
   也让它能离线构建（缓存里已有 flate2 / miniz_oxide）。
2. **我自己在项目根目录创建了一个空的 `Cargo.toml`**：一次
   `[System.IO.File]::ReadAllText("Cargo.toml")` 抛了非终止异常，脚本继续执行
   `WriteAllText`，于是写出了一个 0 字节的文件 —— cargo 随即认为父目录有个非法
   workspace，报的错完全指不到真正的原因。已删除；教训是**用 .NET 静态方法读写
   文件时路径要写绝对**（PowerShell 的 `Set-Location` 不影响进程工作目录）。

## 二十四、第九轮：本地知识库（BM25）

### 1. 为什么自己实现 BM25，而不是用 SQLite 的 FTS5

消息搜索用的是 FTS5 的 **trigram** 分词器（为了中文子串匹配），而 trigram 下
`bm25()` 基本没有区分度 —— 三元组遍地都是，「凌晨三点」和「三点起床」的
trigram 重合度高得离谱。

换成 `unicode61`？它对英文是按词切分的，但**中文没有空格**，整段中文会变成一个
巨大的 token，等于搜不到。

真正的中文 BM25 需要「词」的概念。与其引一个分词库（词典 + 体积），不如自己写：

| 子模块 | 职责 | 关键决定 |
|---|---|---|
| `kb/tokenize.rs` | 分词 | 汉字**单字 + 双字都入索引**；拉丁词按 `_` 与驼峰再切一刀 |
| `kb/chunk.rs` | 切块 | 优先按段落切；只有段落本身超长才硬切，硬切处才留重叠 |
| `kb/rank.rs` | 打分 | 经典 BM25 + 恒正 idf + **确定性排序** |

三个模块都是纯函数，共 29 条单测，不需要数据库、不需要网络。

### 2. 几个「不做就会错」的细节

**单字也要入索引。** 只入 bigram 是 Lucene 的默认做法，代价是**单字查询永远搜不到**
（索引里没有单字）。用户搜「蛋」的时候，他不关心 bigram 是什么。所以两种都入：
个人知识库的规模下索引翻倍无所谓。

**idf 必须恒正。** 经典的 Robertson-Sparck-Jones 公式在「某个词出现在超过一半
文档里」时会给出**负** idf —— 于是命中该词反而扣分。Lucene 早就换成了
`ln(1 + (N - df + 0.5)/(df + 0.5))`，这里照做，并且有一条测试遍历各种 df 断言非负。

**排序必须确定。** 分数相同时按 chunk id 兜底。否则同一份数据两次搜索顺序不同 ——
对用户是「这软件时而聪明时而糊涂」，对测试就是随机失败。

**重叠只出现在硬切处。** 段落之间留重叠会让同一个段落被两段索引两次，
BM25 的文档长度统计跟着失真。段落本身就是语义单元，不需要重叠。

### 3. 删除时必须**重算** df

倒排表靠外键级联删掉，但 `kb_terms.df` 是缓存出来的计数，级联管不着。
不能简单地 `df -= 1`：一个词可能在一篇文档的多个切片里都出现，要减多少得先把
「这篇文档里包含该词的切片数」数出来 —— 逐个算容易错。所以反过来做：
先记下这篇文档用到的所有词，删完之后对每个词**重数一遍**剩下的倒排项。

还有一件事容易漏：**只存在于被删文档里的词必须从词表里删掉**。留着的话
`idf` 会基于一个不存在的词计算，搜索时凭空给分。这两条都有测试盯着。

### 4. 工具接入：条件工具越来越多，别再传 bool 了

原来 `tool_definitions(web_search_enabled: bool)`。再加一个知识库就要多一个
bool 参数，`tool_definitions(true, false)` 这种调用过一个月就没人记得哪个是哪个。
所以换成了 `ToolAvailability { web_search, knowledge_base }` 结构体 ——
将来的 MCP 也只是再加一个字段。

两条延续下来的原则：

- **库是空的就不下发这个工具**（与 `web_search` 未配置时一致）。让模型看到一个
  必然空手而归的工具，只会白烧一轮 token；
- **不给模型看 score**。`0.8735` 对它没有意义，只会被原样抄进回答
  （「根据资料（相关度 0.87）…」）—— 看着像那么回事，其实是在展示一个对读者
  毫无信息量的内部指标。工具输出只给「标题 + 第几片 + 正文」，这也是让模型
  能标出来源、用户能回去核对的最小信息。

## 二十五、第十轮：长期记忆

### 1. 与知识库的分工，以及「记忆刻意不建索引」

|  | 知识库 | 长期记忆 |
|---|---|---|
| 内容 | 用户主动导入的资料 | 从对话里沉淀的、关于用户的事实 |
| 规模 | 可能上万片 | 几百条以内，一条就是一句话 |
| 索引 | 倒排表 + df 维护 + 删除重算 | **没有索引**，检索时遍历现算 |
| 入口 | 用户导入 | 模型自己记（`remember`）+ 用户手动加 |

第二行的差异决定了第四行：**索引的价值随语料规模增长，在小语料上它只是债**。
几百条一句话的记忆，遍历 + 现算 BM25 的代价可以忽略；而维护 df 增减、
删除时重算、切片与原文对应这些复杂度，只有在知识库那种规模下才划算。

这个取舍写在这里，是因为它很容易被反过来「优化」掉 —— 看到知识库有倒排表，
顺手给记忆也加一份，代码变多、bug 面变大，而收益是零。

### 2. 去重：Jaccard 被测试打回来了

记忆库最容易变脏的地方是「同一个意思换个说法加二十遍」，而每次能注入的只有几条
—— 等于把真正有用的挤出去。所以写入时要判重。

第一版用的是 **Jaccard**（`|A∩B| / |A∪B|`）：

```rust
pub fn similarity(a: &[String], b: &[String]) -> f64 { /* Jaccard */ }
```

测试直接把它打回来了：「用户喜欢用 Rust 写程序」和「用户喜欢用 Rust 写代码」
是**明显该合并的重复**，但在这套「单字 + 双字」分词下 Jaccard 只有约 **0.58**
—— 因为两种写法各自都会产生十几个不同的字/双字 token，分母被撑大了。

换成**重叠系数**（`|A∩B| / min(|A|,|B|)`）：它衡量的是「短的那条是不是基本被长的
那条包含」，而这正是「同一个意思换个说法」的形态 —— 中文里换说法往往就是加几个字
或换一个词。同例重叠系数约 0.73，过线。

代价是「短句是长句子集」时会偏高（「Rust」与「用户喜欢用 Rust 写程序」重叠系数是
1.0），所以判定重复必须**同时**要求共享 token 数达标（`MIN_SHARED_TOKENS`）——
这条也有单独的测试盯着（`a_short_memory_is_not_swallowed_by_a_longer_one`）。

### 3. 一个被记忆测试暴露出来的**知识库**的缺陷

写完记忆测试后，这条红了：

```rust
assert!(db.memory_relevant("量子力学", ...).unwrap().is_empty());
```

结果不为空 —— 因为「用户的猫叫**团子**」里有「子」，而索引里存了单字。

根因是上一轮为了「单字查询也能搜到」而让索引存了单字 + 双字，**查询时也把单字带上
了**。于是任何含「子」的文本都会被「量子力学」命中。这个问题知识库里同样存在，
只是那边文档多、idf 低，噪音排在后面不明显。

修法是让索引与查询**不对称**：

| 侧 | 汉字长串 | 单字串 |
|---|---|---|
| 索引（`tokenize`） | 单字 + 双字都存 | 存 |
| 查询（`query_terms`） | **只用双字** | 用单字 |

这样「一个字也要能搜到」没丢（单字查询没有双字可用，自然落到单字），
而「搜『量子力学』命中『团子』」这种噪音消失了。修完这一条，知识库的检索精度
也顺带提高了一档 —— **一个功能的测试暴露了另一个功能的缺陷**，这只有在两边
共用同一套纯函数（分词器）时才可能发生。

### 4. 默认关闭，而且注入只做一次

打开长期记忆意味着「每次提问都把本地存下来的用户信息发给服务商」。这个项目既有的
立场是「工具默认关闭、读过本地敏感数据要再确认一次」，所以这里也**默认关**，
由用户明确打开（界面上把这句话直接写出来，而不是藏在文档里）。

另外两点：

- **注入只在每条请求里做一次**，不是在每一轮工具循环里做。多轮工具调用复用同一份
  系统提示词，重复注入只会让它们互相矛盾；
- **检索失败不影响聊天**：记忆是锦上添花，查询失败记一条诊断日志、继续把消息发出去。
  让「查记忆」这种附加功能把主流程弄挂，是最不能接受的一类 bug。

### 5. 提示词里的两句话

拼进系统提示词的块是这样开头的：

> 以下是之前对话里记下的、关于用户的背景信息，供参考（**可能已经过时，不确定就不要
> 用**，也不要主动提起这些信息的来源）：

- **「可能已经过时」**：记忆会过期（用户换了技术栈、项目做完了）。不提醒的话，模型
  倾向于把记忆当硬事实，说出「你之前说你喜欢 X」这种已经不对的话；
- **不提「记忆」这个词**：告诉模型「以下是关于用户的背景」，比「以下是你的记忆」更
  像正常背景信息，模型也更不容易在回答里冒出「根据我的记忆」这种让用户发毛的话。
  这条有测试守着（`assert!(!block.contains("记忆"))`）。

### 7. 我自己的三个错

1. **同毫秒插入的顺序**：测试期望「后加的排在前面」，但两条记忆是在**同一毫秒**内
   插入的，而我的排序是 `created_at DESC, id ASC` —— id 是字典序，于是先加的排前面。
   产品行为确实不对（同一毫秒内也该按插入顺序），把兜底改成 `rowid DESC` 才是对的。
   **测试又抓到一个真问题**，只是这次的表现形式是「测试失败看起来像期望写错」。
2. **上限测试的数据太像了**：我用 `第 {i} 条互不相同的记忆内容 abc{i}` 塞 500 条，
   结果它们被**去重合并成 1 条** —— 测的是去重，不是上限。改成用 SQL 直接预填。
   （这个失败本身倒是去重有效的旁证。）
3. **PowerShell 单引号里的 `` `n ``**：我用 `-creplace` 往 TSX 里插多行 import，
   单引号串里的 `` `n `` **不会被转义**，于是字面量 `` `n `` 被写进了源文件。
   教训与之前那次「双引号里的 `\"` 提前结束字符串」是同一类：**用 shell 拼源码
   迟早出事**，能用编辑工具就用编辑工具。

## 二十六、第十一轮：一问多答（模型对比）

### 1. 先讲**不做**什么：不动主动聊天的那条不变式

主动聊天里最关键、也最难写对的一条是：

> 一个会话同时只有**一条**在飞的助手消息。

`ChatStreamState.live` 就是按**会话**索引的单条。这条不变式换来的是
「回答到一半切到别的会话，那条回答不会丢；切回来它还在继续长」。

一问多答要在同一时刻跑 N 条回答。把 N 条塞进那个按会话索引的 `live`，
等于把上面这条不变式拆掉 —— 而它正是主动聊天里最值得保住的部分。
为一个**不需要它**的功能去改它，风险与收益完全不成比例。

所以这一轮的做法是：**对比面板自带一套路由**，压根不碰 `live`：

|  | 主动聊天 | 一问多答 |
|---|---|---|
| 状态 | `useChat`（单条在飞） | `useCompare`（N 条并排） |
| 落库 | 写进会话 | **不写**（`conversationId: null`） |
| 出口 | 气泡进聊天流 | 草稿纸；看中了「采用这条」 |

「不落库」不是省事，而是后端设计顺带给出的：落库那几处都是
`if let Some(conversation_id)`，所以 `conversationId: null` 天然不写库。
对比本来就该是草稿纸 —— 试四个模型的答案都堆进聊天记录，历史会变得没法看。

### 2. 复用 `chat_send` 就够了

对比不需要新命令：`chat_send` **立刻返回**（真正的流在后面 `spawn`），
所以并发发 N 次是自然的。每个请求带一个前端生成的 `requestId`，
事件回来后按 `requestId` 分发。

两个必须显式关掉的开关：

- `conversationId: null` → 不落库（上面说过）；
- `enableTools: false` → 一路请求可能弹工具审批，N 路就会**同时弹 N 个审批框**，
  而对比面板根本没有处理审批的界面，只能干等超时。对比关心的是回答质量，
  本来也不需要工具。

### 3. 只加一个命令：采用

`adopt_answer` 把选中的那一问一答写进会话。为什么**连问题一起写**：
对比面板里的问题不在会话历史里，只写回答的话，会话里会出现一条没有提问的回答，
用户往后翻会看得莫名其妙。

写入时机也有一条规则：空回答、报错、被取消的**都不允许采用**
（`canAdopt`）—— 否则会话里会多出一个空气泡。

### 4. 验证：真浏览器里数出四列

这一轮的界面验证走的是已有的像素探针工具（`tools/preview-client.tsx`）：
把 store 直接设成「跑完的」状态再挂载面板，于是在无头浏览器里能真的检查：

| 检查项 | 结果 |
|---|---|
| 渲染出 4 列 | ✓ |
| 三列有内容、一列报错 | ✓ |
| 流式列显示「生成中…」 | ✓ |
| 采用过的显示「已采用」 | ✓ |
| 每列都有「采用这条」 | ✓ |
| 失败那列没有内容但有错误 | ✓ |

加上原有的 11 项（KaTeX / 高亮 / mermaid），探针 **17/17 全绿**。

### 5. 又一次「红的是尺子」

第一次跑的时候，高亮配色那 4 项检查**全部 0 命中**，看着像高亮坏了。

原因是新加的面板用了 `position: fixed` 的遮罩（真机上要盖住整个窗口），
而验证页里那些用来查配色的样例就在它**下面** —— 整页被压暗 45%，
精确配色自然一个都匹配不上。

修法是给挂载点加一条作用域内的覆盖样式（`#compare-host .compare-backdrop
{ position: static }`），让面板在验证页里老实待在自己的位置。

这条已经在这个项目里出现过好几回了：mermaid 的 2 项红（验证页自己没引 KaTeX
的 CSS）、剪贴板的红（环境里有个进程占着剪贴板）、高亮 number 的 0 命中
（样例里没有数字字面量）。**检查红了先怀疑尺子**，比怀疑产品更快找到真因。

### 6. 其它

- `streamingIds` 之类的状态没有被引入：对比面板的每一路自带 `streaming` 标记，
  「还在跑」= 有几路的 `streaming` 为真。
- 上一轮没跑完时不允许开新一轮（`streamingCount > 0`）—— 两轮结果混在一个
  列表里，用户分不清哪条是哪次问的。
- 目标去重按「服务商 + 模型」：同一个模型对比两次毫无意义，而消耗是实打实的。

## 二十七、第十二轮：技能（Skill）

### 1. 先说清楚它和「角色」的区别

项目里**已经有**角色预设（`Role { id, name, prompt, builtin }`）：挂在会话上、
输入框上方可切换。如果新加的「技能」只是「能按消息切换的角色」，那它就是角色的
别名，不该存在 —— 只会让用户面对两个看起来一样的东西。

所以先把差别定死：

|  | 角色 | 技能 |
|---|---|---|
| 作用范围 | 整个会话（绑在会话上） | **只有这一条消息** |
| 回答什么 | 「你是谁」——持久的身份 | 「这次做什么」——一次性的任务 |
| 工具 | 不干预 | **可以指定这次用哪些工具** |
| 触发 | 下拉框 | 下拉框 **或 `/名字` 斜杠命令** |

真正让它独立的那个能力是**工具白名单**：「联网调研」需要搜索与抓网页，
「纯离线总结」则必须一个联网工具都不给。角色管不了这件事，而它恰恰是用户
真正在意的那类开关（数据出不出得去）。

### 2. 白名单必须在后端强制执行

一条原则在这个项目里反复出现：**前端能控制的是「模型看到什么」，控制不了
「模型硬调什么」**。模型完全可以凭名字调用一个没下发的工具。

如果只把工具从清单里过滤掉，那么「纯离线总结」这个技能是**假的**：
被硬调一次 `web_search`，数据就发出去了 —— 而它存在的全部意义就是不让数据出去。

所以两层都拦：

| 层 | 做法 |
|---|---|
| 下发 | `tools_for(availability, whitelist)` 过滤清单 |
| 执行 | `ToolContext.allowed` 在执行入口再拦一道，拒绝时给出明确理由 |

另外一条同样重要：**白名单只能收窄，不能放开**。「联网调研」点了名 `web_search`，
但用户根本没配搜索端点 —— 此时不能凭空把它放出去，否则模型会去调一个必然
失败的工具、白烧一轮 token（这条原则从工具清单那会儿就定下了）。这条有专门的
测试（`a_whitelist_cannot_unlock_a_tool_that_is_not_available`）。

### 3. 长期记忆也得能被技能关掉

写白名单的时候发现一个漏洞：**长期记忆的注入不是工具调用**，它是把本地存下来的
用户信息拼进系统提示词发出去 —— `tools_for` 那套过滤**管不到它**。

于是「纯离线总结」会出现自相矛盾的行为：一边关掉所有联网工具，一边把用户档案
发出去。

修法是给技能加一个「能力」判定（`skill_allows_capability`），目前只有长期记忆用
它。这类东西将来还会变多（任何「不叫工具但会外发数据」的机制），所以判定入口
从一开始就按「能力名」而不是「工具名」来写。

### 4. 斜杠命令的三条规则

`/翻译 这段文字` 这种写法比下拉框快得多，但它很容易做得让人困惑。三条规则：

- **必须整条消息以 `/` 开头**：「价格是 3/5」不该被当成命令；
- **名字按名字或 id 匹配，忽略大小写**：中文名不受影响，英文名要好敲；
- **后面必须有内容**：只有 `/翻译` 一个词时按普通文本发出去。否则会往模型那里
  送一条**空的用户消息** —— 那比「没生效」更让人困惑。

还有一条优先级：**斜杠命令优先于下拉框的选择**。用户手打了 `/翻译` 却因为下拉框里
还挂着上一次选的技能而没生效，是很难自己想明白的。

### 5. 工具名写错要报错，不能静默丢弃

技能的 `tools` 里写了一个拼错的名字（`web_seach`），后果很隐蔽：技能看起来完全
正常，但那个工具**永远不生效**（清单被过滤掉了），用户只会觉得「开了也没用」。

所以后端 `sanitize_skills` 对未知工具名**直接报错**，并且在消息里说清是哪个技能、
哪个名字。界面上则进一步：工具那栏做成**勾选已知工具**，根本不给写错的机会。

### 6. 验证

| 层 | 手段 |
|---|---|
| 纯逻辑（前端） | 16 条：命令解析（普通文本里的 `/` 不算、不认识的名字不算、只打命令没内容不算、多行保留、忽略大小写、也认 id）、优先级、安静回落、标签与工具说明、新 id 不重复 |
| 解析器（Rust） | 6 条：规整（去空格 / 空项 / 重复 id / 上限）、空名字空指令拒收、**未知工具名报错且说清是哪个技能**、预设本身能过自己的校验、只有该限制工具的预设才限制 |
| 白名单（Rust） | 4 条：只留名单内的、**不能放开没配好的工具**、执行入口拒绝名单外的、名单内的照常跑 |
| 能力判定（Rust） | 1 条：限制工具的技能可以关掉记忆注入；不限制的不管；点名了记忆的允许 |
| store | 1 条：技能 id 真的进到请求里（不选时显式传 `null`） |
| 真机 | 构建 + 启动可见 |

结果：Rust **327 passed**、前端 **300 passed**。

### 7. 又一次「测试第一次就写错」

新加的那条 store 测试第一次跑就红了，红的原因是**我自己的测试**：连发两条消息时
没有清掉第一轮的「在飞」状态，于是并发闸门把第二条拦住了 —— 断言实际测的是闸门，
不是技能字段。修法是发送前显式清掉 `streamingId`。

这类错在这几轮里出现得最多（同毫秒排序、上限测试数据被去重吃掉、单字母被分词器
丢掉、验证页遮罩压暗配色）。它们的共同点是：**失败信息指向产品，真因在测试**。
所以看到红的第一件事应该是问「这个断言真的在测我以为的那件事吗」。

## 二十八、第十三轮：文生图

### 1. 为什么走 `images/generations`，而不是引一个「图片服务商」

`POST /images/generations` 已经是事实标准（OpenAI、智谱、通义、SiliconFlow 等
一大批都实现了它）。于是文生图**不需要新的服务商概念**：复用用户已经配好的那份
Base URL 与 API Key，只把端点从 `chat/completions` 换成 `images/generations`。

模型名则是**单独填的**，不放进服务商的模型列表：能聊天不代表能画图
（`gpt-4o` 不是 `gpt-image-1`），混在一起只会让用户以为「列表里有就能画」。

### 2. `response_format` 的两难，以及为什么必须重试

这个字段是本次实现里最值得写下来的一处兼容问题：

| 模型 | 行为 |
|---|---|
| DALL·E 一类 | **需要** `response_format: "b64_json"` 才会直接给 base64，否则只给一个临时 URL |
| gpt-image-1 一类 | 收到这个字段直接 **400**（它总是返回 base64，不再接受该参数） |

两边都要能用，所以策略是：**先带上，被明确拒绝就去掉再试一次**。

判断「是不是因为这个字段被拒」只能靠错误文本（服务商在这件事上给的信号只有文本），
所以匹配写得很窄：状态码必须是 400/422、文本里必须出现 `response_format`、
并且还要出现 `unknown parameter` / `unsupported` / `invalid` 之类的词。
不这么窄的话，任何一个 400（内容审核、额度用尽）都会触发一次无谓的重试。

这条路径有真 TCP 服务器的测试：断言第一次请求**带着**该字段、第二次**不带**、
且总请求数**恰好是 2**。

### 3. 两个安全细节

**下载第三方图片 URL 时不带 API Key。** 服务商返回的 URL 常常指向 CDN，
把密钥发过去等于把凭据交给一个不相关的域。图片下载本来也不需要鉴权
（需要鉴权的服务商直接返回 base64）。

**先看 `Content-Length` 再读，读完再核对一次实际长度。** `resp.bytes()`
会把整个响应读进内存，一个被构造出来的超长响应就是一次内存打满的机会。
上限 12 MB 也来自同一个考虑：图片要以 base64 塞进消息（再翻 1.33 倍）、
存进数据库、每次读会话都读出来 —— 不设上限的话几张图就能让会话变得又慢又占地方。

**格式按字节头识别，不信服务商也不信 URL 后缀。** `data:` URL 的 mime 一旦
写错，WebView 会**静默地什么都不显示** —— 那是最难查的一类表现。

### 4. 「提问 + 带图回答」必须一次写完

前端分两步（先存提问、再存图）会留下「提问写进去了、图那步失败了」的中间状态：
会话里一条没有回答的提问。所以 `append_image_turn` 在后端一个事务里把两条都写掉。

助手那条的**正文是一句说明**（「🎨 已按…生成图片」），图片挂在 `images` 字段上 ——
这样它在历史里既**能被搜到**（有文字），又**能被渲染成图**（有图）。
只放图不放文字的话，消息搜索会漏掉它。

### 5. 关于「自动更新」和「PDF」：先探测依赖，再决定做不做

这一轮开工前先查了本地 cargo 缓存（这台机器上 `static.crates.io` 解析不了，
新 crate 装不进来）：

| 需要的东西 | 缓存里 |
|---|---|
| `tauri-plugin-updater`（自动更新的官方插件） | ✗ |
| `lopdf` / `pdf-extract`（PDF 解析） | ✗ |
| `image` / `png` | ✓（用不上，因为图片直接走 data URL） |

所以这一轮选了**不需要任何新依赖**的文生图。这个「先探测、再选活」的习惯值得
保留：否则会在一个装不上依赖的功能上耗掉一整轮，最后只能推翻重来。

### 7. 又一次：我把「形态不对」写成了静默回落

`validate_size("1024X1024")`（大写 X）我第一版实现成「形态不对就回落默认值」，
测试里也这么期望的。写测试时才想明白这是错的：用户填 `1024X1024` 想要的是方图，
静默给他默认值等于「要了竖版拿到方的」—— 而且他永远不会知道。

改成明确报错，并把**原值**回报给他（「要写成『宽x高』，收到的是「1024X1024」」）。
原则是：**「没说」可以回落默认，「说错了」必须报错。**
