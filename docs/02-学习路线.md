# 02 · 学习路线与动手清单

这份文档回答三个问题：**先读哪个文件**、**每个文件要看出什么**、**读完之后自己动手做什么**。

---

## 零、先跑起来

```bash
npm install
npm run tauri:dev
```

第一次 `cargo` 要编译约 450 个依赖，10–20 分钟属于正常。之后增量编译是秒级。

应用起来后：

1. 点标题栏 ⚙ → **模型** → 找到 DeepSeek → 粘贴 API Key → 保存；
2. 点「测试连接」确认链路通；
3. 关掉设置，输入一句话，看流式回答一个字一个字出来；
4. `Alt+Space` 收起再唤出；点 ⤢ 展开完整模式，看历史侧栏；
5. 打开输入框上面的 **🔧 工具开关**，问「现在几点」「算一下 (3+4)*2」；
   再让它「读一下我的剪贴板」—— 这时会弹出**审批卡**，这就是三级授权的入口；
6. 在别的程序里选中一段文字，按 `Alt+Q`（若被别的软件占用，去
   **设置 → 通用 → 划词快捷键** 改一个）。

**跑通再读代码。** 一个能运行的对照物比任何文档都值钱。

## 一、阅读顺序（按依赖关系，不是按目录顺序）

### 第一轮：把「一条数据怎么走完全程」搞明白（约 2 小时）

| 顺序 | 文件 | 要看出什么 |

读完这 7 个文件，你应该能画出「一次对话的时序图」而不用回头看。
画不出来就再读一遍 —— 这是整个项目的骨架。

### 第二轮：三个最有技术含量的模块（约 4 小时）

| 顺序 | 文件 | 要看出什么 |
|---|---|---|
| 1 | `src-tauri/src/api/sse.rs` | 为什么按裸字节 `0x0A` 切行是 UTF-8 安全的；`finish()` 为什么必须存在；两个上限在防什么 |
| 2 | `src-tauri/src/api/openai.rs` | 语义层与字节层怎么分工；`finish_reason: ""` 这个坑；错误分类表 |
| 3 | `src-tauri/src/api/stream_client.rs` | 重试**只**在流开始之前；`finish_reason` 后的 usage 宽限期；取消怎么和读取同时等 |
| 4 | 同文件的 `mod tests` | **这是本项目最值得学的地方**：起本地假服务端、跑真实 HTTP，把 12 个线上形态钉死 |

两份测试要对照着看：

- `every_multibyte_char_split_at_every_offset` 把含 `你好世界🌍` 的 payload 在
  **每一个字节位置**切开，断言结果与一次喂进去完全一致 —— 「用测试把一整类 bug
  钉死」，比写十个手写 case 有用得多；
- `content_and_done_in_the_same_chunk_is_not_lost` 是一个**回归测试**，
  它对应的 bug 是「正文和 `[DONE]` 落在同一个 TCP 分片时，正文进了库却从来没
  显示出来」。这个 bug 是写测试的过程中才发现的。

顺便看 `drain_request` 这个测试辅助函数：它把请求**读干净**再回包，因为
Windows 上关闭 socket 时若接收缓冲区还有数据，内核会发 RST，可能把刚写出去的
响应一起干掉 —— 不处理的话测试会随机失败。

这一轮是第四轮（专项审计）新增的。**它和前七轮的读法完全不同**：
前七轮是顺着依赖关系读「正确的代码长什么样」，这一轮是读**坏掉的代码长什么样、

| 顺序 | 看什么 | 要看出什么 |
|---|---|---|

| 2 | `src-tauri/src/agent/context.rs` 的 `fit_context_with_summary` | 为什么「定位失败就整段放弃摘要」是**正确**的降级方向（宁可多发历史，不能丢提问） |
| 3 | 同文件 `a_stale_boundary_never_swallows_the_current_question` | 回归测试怎么写：直接把「摘要声称 40 条、数组只剩 6 条」这个矛盾摆出来 |
| 4 | `src/storage/config.rs` 的 `load` + `recover_from_unusable` | 为什么 `Err(_)` 是危险的；`NotFound` 和 `InvalidData` 的区别为什么关乎数据存亡 |
| 5 | `src/tools/web.rs` 的 `strip_element` | `<head` 前缀匹配为什么会吃掉 `<header>`；「找不到闭合标签」在两个标签上要有相反的处理 |
| 6 | `src/lib/toasts.ts` + `src/components/Toasts.tsx` | 「状态只写不读」这种缺陷为什么单元测试抓不到、而要靠**审计**；把展示逻辑抽成纯函数的收益 |
| 7 | `src/stores/chat.ts` 的 `submit` / `settleConversation` | 并发闸门为什么必须在**第一个 `await` 之前**同步落下；结算为什么要带上「结算的是哪一条」 |
| 8 | `src/stores/chat.test.ts` | 不用 DOM、把 IPC 全 mock 掉，怎么把竞态写成确定性测试 |
| 9 | §十三 第 9 节 + `tools/web.rs` 的 `the_configured_proxy_is_actually_used_by_the_web_tools` | **「参数加了」不等于「参数被用了」**：接线类 bug 不报错，只让功能时灵时不灵；以及怎么用一个假代理把「真的走代理了」变成可断言的证据 |

> 这一轮最该带走的一句话：**「能跑」和「正确」之间隔着很多条只在特定时序下
> 才暴露的路径**。前七轮教你怎么把功能搭起来，这一轮教你怎么怀疑自己搭的东西。

## 二、动手练习

> **注意**：下面练习 2–5 描述的功能**已经在代码库里实现了**（第三轮 P0/P1）。
> 所以这几个练习改成两步走：
> **① 先自己按提示实现一遍**（不要看代码），**② 再对着真实实现 diff 自己的思路**。
> 每节都标了「实现在哪」，方便第 ② 步。
>
> 直接看代码也能学到东西，但「先自己想一遍再看」的收获要大得多 ——
> 尤其是下面几个**测试抓出来的坑**，自己踩一次印象会深很多。

### 练习 1 · 加一个第三个热键（30 分钟）

`window/shortcuts.rs` 现在同时注册**两个**键（唤醒 `Alt+Space` + 划词 `Alt+Q`），
`configured()` 返回 `(String, Option<String>)`，`register_all` 按一组键逐个注册。
顺着这个结构加第三个：「展开/收起完整模式」（默认 `Alt+E`）。

需要改：
- `AppConfig` 加字段（注意：加了字段就等于加了一次配置迁移，旧 `providers.json`
  没有这个字段时必须能正常反序列化 —— 这就是容器上 `#[serde(default)]` 的作用）；
- `shortcuts::configured` 的返回类型（现在是二元组，加第三个就变三元组了 ——
  想过没有？这时候该不该换成一个 `struct ShortcutSet`？）；
- `lib.rs` 的 handler 要区分按的是哪一个键（现在是 `is_quick_action` 二选一，
  三个键就需要一个「按下的键 → 动作」的映射）。

**坑**：`register_all` 里先 `unregister_all()` 再逐个注册 —— 如果中途失败，
会把能用的键也一起撤掉。想想怎么改成「先注册新的，成功了再撤旧的」。

### 练习 2 · 消息编辑与重新生成（1–2 小时）

先自己写：双击用户气泡进入编辑态（本地草稿，Esc 取消、回车提交），提交时
① `update_message` 改内容，② 把这条**之后**的消息从数据库和界面上都删掉，
③ 用「这条之前的历史 + 编辑后的内容」走 `submit`。

**实现在哪**：`stores/chat.ts` 的 `editAndResend`、`components/MessageList.tsx`
的 `MessageBubble`（`editing` / `draft` 两个局部 state）。

**坑 1**：编辑**已有**的用户消息时，`newUserText` 要传 `undefined`，只调
`update_message` 改内容 —— 否则同一句话会存两份（`regenerate` 踩过这个坑）。

**坑 2**：只能编辑**已落库**的消息。还没落库的乐观气泡 id 是 `local_` 前缀，
数据库里没有对应行，改它会静默失败。

**坑 3**：删除消息时 FTS 索引会跟着触发器自动更新，不需要手动重建
（但值得写一条测试确认，见 `deleting_a_conversation_clears_its_search_index`）。

**扩展**：现在「重新生成」会删掉旧回答。想保留多版本的话，
参考 `analysis/04` 里提到的「行内 JSON 版本栈」。

### 练习 3 · 滚动摘要（半天）

先自己写：上下文超预算时，把要丢的那一段交给模型压成摘要，存进数据库，
下一轮把「摘要 + 之后的原文」发给模型。

**实现在哪**：`agent/summary.rs`（纯逻辑：该不该摘 / 折叠哪一段 / 提示词怎么拼）、
`agent/context.rs::fit_context_with_summary`（摘要装配）、
`commands/chat.rs::maybe_summarize`（网络调用 + 落库）、迁移 v9 / v10。

**坑 1**：折叠边界必须落在一条 `user` 消息上。把「提问」折进摘要、把「回答」留在
原文里，剩下的上下文就以 `assistant` 开头 —— 不少服务端会直接 400。

**坑 2**：摘要自己也要吃预算（它是一条真实的 `system` 消息），
所以要先扣掉它的 token，再让原文去抢剩下的额度。

**坑 3**：`dropped`（真丢了）和 `summarized`（改用摘要替代）必须是**两个**字段。
混在一起，前端会提示「已省略 50 条」，而实际上一条都没丢。

**坑 4**：写摘要时**不要**动会话的 `updated_at` —— 后台压缩不该让一个旧会话
跳到会话列表最前面。

**扩展**：参考项目在这里有个真实缺陷 —— 它的 `fit_context` 在知识库、技能、
搜索结果注入**之前**执行，于是那几块完全不受预算约束。本项目的做法是
「所有注入都发生在裁剪之前」，你可以验证一下：加一个新的注入源，
看它是否自动受预算约束。

### 练习 4 · 接入一个内置工具（半天）

先自己写：加一个「获取当前时间」工具。

**实现在哪**：`tools/registry.rs`（`ToolDefinition` + `match` 分发 + 六道导出规则）、
`api/openai.rs::messages_to_openai`（tool_calls / tool 消息的规范形态）、
`api/stream_client.rs::consume_stream`（按 `index` 累积分片）、
`commands/chat.rs::run_stream`（agent 循环 + 审批）。

**坑 1（最大的坑）**：拒绝执行、工具不存在、参数解析失败这几种「**根本没执行**」
的情况，**也必须**造一条 `tool` 消息回灌，否则下一轮请求会被服务端 400 拒绝
（「有 tool_calls 却没有对应的 tool 结果」）。

**坑 2**：工具参数是**分片**到达的（`{"path": "a` 和 `bc.txt"}` 是两帧），
而且 `id` / `name` 只在第一片出现。要用 `BTreeMap<usize, …>` 按 `index` 累积。

**坑 3**：工具的**策略字段**（要不要审批、会不会外发数据）绝不能出现在
`to_openai_tools` 的导出结果里 —— 模型拿到只会尝试绕过。
有一个单测把导出结果序列化成字符串来断言这一点。

**扩展**：给 `run_stream` 的 agent 循环写单测。它现在依赖 `AppHandle` 所以测不了 ——
把「执行工具 + 组装回灌消息」抽成一个不依赖 Tauri 的纯函数，就能测了。
这是本项目当前**最值得补的一处测试空缺**。

### 练习 5 · 划词助手 `Alt+Q`（1 天）

先自己写：Windows 没有「读取当前选区」的 API，通行做法是
**保存剪贴板 → 模拟 Ctrl+C（`SendInput`）→ 轮询剪贴板 → 还原剪贴板**。
参见 `analysis/06` 的 §A.5。

**实现在哪**：`window/quick_action.rs`。

**坑 1**：必须等修饰键松开再发 `Ctrl+C`。热键触发时 `Alt` 还按着，
注入的按键会变成 `Alt+Ctrl+C`，没有程序会把它当复制。用 `GetAsyncKeyState` 轮询。

**坑 2**：**窗口必须在复制之后才显示**。模拟按键只到达「当前拥有选区的窗口」；
先把助手窗口显示并聚焦，按键就打进自己的输入框了，取词永远失败。

**坑 3**：轮询到的新内容和按热键前**一模一样**时，说明复制根本没发生
（没选中东西，或目标窗口被 UAC 挡住），继续等是白等。

**已知限制**：对管理员权限（UAC 提升）的窗口无效 —— 这是 Windows 的限制，
不是 bug。要有明确的错误提示，而不是静默失败。

**扩展**：`Alt+Q` 很抢手，设置里已经能改。想一想：改键时为什么要
「**先注册再落盘**」而不是反过来？（提示：反过来会在注册失败时留下一个
「配置里写着一个抢不到的键」的死状态，用户重启也回不来。）

### 练习 6 · 图片输入（半天）

先自己写：粘贴 / 拖入一张图 → 缩略图 → 发送时变成多模态消息
（`content` 从字符串变成 `[{type:"text"},{type:"image_url"}]`）。

**实现在哪**：`api/openai.rs::messages_to_openai`（数组形态 + 顺序）、
`commands/history.rs`（data URL 白名单 + 数量体积上限）、
`storage/database.rs`（迁移 v11 `images_json` + `images_for_ids` 批量查）、
`commands/chat.rs::attach_images`（按 id 回填）、`components/Composer.tsx`。

**坑 1（最容易漏的一个）**：图片**不要**跟着历史走 IPC。本项目每次请求都会把整个
会话历史发过来，如果图片也塞在里面，一个 10 轮 × 2 张图的会话每次提问就要搬
几十 MB。正确做法是「前端只回传消息 id，后端按 id 从库里取图」。
但这样一来，`submit` 里必须把历史中那条**刚落库**的用户消息补上 id ——
不补的话，刚发出去的那张图这一轮反而看不到（追问一次才生效）。

**坑 2**：`content` 保持 `String`，只在适配器里展开成数组。
把它改成 `Text | Vec<ContentPart>` 的枚举会牵动 `estimate_tokens`、
`fit_context`、`summary`、落库、搜索一大片代码，收益却只是类型更精确。
**把复杂度收在一处**比散到十处好维护。

**坑 3（安全）**：图片最终要进 WebView 的 `<img src>`，所以 data URL 必须用
**白名单**。`data:text/html` 能执行脚本，`data:image/svg+xml` 里能塞 `<script>`
或 `onload=` —— 黑名单永远会漏。

**坑 4**：`paste` 事件只在真的带图时才 `preventDefault`，否则会把正常的文字粘贴弄坏。

**扩展（真实待办）**：现在图片是**原样**发送的，手机拍的照片动辄几 MB，
既费 token 又费流量。前端在读取之后先画到 `canvas` 上压到长边 1568px，
再 `toDataURL("image/jpeg", 0.85)` —— 试试能把体积压掉多少。

### 练习 7 · 亲手制造一个时序 bug，再用测试钉死它（1 小时）

这一轮修掉的几个前端缺陷都有同一个特征：**只在特定的时序下才出现**，
手工点界面很难稳定复现。所以练习的方式反过来 —— 先故意写坏，再写测试。

以「结算误删新一轮」为例（`src/stores/chat.ts` 的 `settleConversation`）：

1. 把现在的实现改回旧写法：忽略 `settled` 参数，直接
   `dropConversation(s, conversationId)`（也就是「按会话清干净」）；
2. 跑 `src/stores/chat.test.ts` 里那条「结算期间新发起的请求不会被误删」——
   它应该**失败**。这一步很重要：先确认测试真的能抓到这个 bug，
   否则你写的可能只是一条永远为真的断言；
3. 再把实现改回来，确认测试变绿；
4. 换一条自己找：`send` 里把 `set({ submitting: true })` 挪到
   `createConversation` **之后**，看并发闸门那条测试会不会失败。

**要体会的点**：先有「能失败的测试」，再有修复。反过来的话，
你无法区分「修好了」和「根本没测到」。

### 练习 8 · 补齐一个「后端有、前端没有」的能力（1–2 小时）

审计里发现了一批这种能力。已经补上的有：自定义服务商的增删、永久授权的撤销、
系统代理开关、会话列表分页。**还没补的是 `messages_before`**：

- `src-tauri/src/commands/history.rs` 的 `messages_before(id, limit)` 早就写好了；
- `src/services/api.ts` 里的 `api.messagesBefore` 也有；
- 但**没有任何组件调用它**：`get_conversation` 永远把整个会话一次读完。

要做的：在消息列表顶部加一个「加载更早的消息」，往上翻到头时按需拉取。
技术难点不在 IPC，而在 `react-virtuoso` 的 `firstItemIndex` ——
往头部插入数据时必须同步递减它，否则滚动位置会跳。试试看你能不能复现出
「不递减会跳」，以及 `increaseViewportBy` 要调成多少才不闪。

## 六、一句话总结这个项目教了什么

> **把不可靠的外部世界（网络、模型、系统窗口）变成可靠的状态机。**

五条具体经验：

1. **协议设计能消灭的竞态，不要用锁去解决**（`requestId` 由前端生成）；
2. **每一处外部字节都要有上限**（SSE 行 1 MiB / 事件 8 MiB / 错误体 128 KiB /
   抓取响应 512 KiB）；
3. **用测试把一整类 bug 钉死**，而不是逐个修补
   （在每一个字节位置切开 UTF-8 payload）；
4. **不可测的代码 == 没被验证的代码**。第一轮把流式循环从 Tauri 命令里拆出来，
   才有了那些真开 TCP 端口的集成测试 —— 而写这些测试的过程本身又抓出了
   两个真 bug：「正文进了库却从没显示」，以及 SSRF 里 `http://[::1]/`
   绕过全部内网拦截；
5. **静默降级比报错更糟**。上下文被裁剪、历史被省略，都必须让用户看见；
   反过来，`AppError{code, message, retryable}` 这种结构化错误让前端能按类型
   分支，而不是去猜中文字符串。

第三轮又加了一条，而且是安全意识上最重要的一条：

6. **模型的输出是不可信输入**。它给的 URL、它要调的工具、它的参数，
   都要按「这是攻击者写的」来对待：
   - 策略字段（要不要审批）绝不能下发，否则等于把门锁的图纸给小偷；
   - 参数要过白名单（计算器不用 `eval`）；
   - 联网地址要过 SSRF 闸门，而且**必须用解析器给出的类型**判断 IP，
     不能靠字符串长相 —— `[::1]` 那个绕过就是这么来的；
   - 「读过本地数据」这件事要作为状态传下去，影响**后续**的决策
     （数据流防泄漏：再发给模型前二次确认）。
